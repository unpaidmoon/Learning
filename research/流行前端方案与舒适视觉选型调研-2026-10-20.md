# 流行前端方案与舒适视觉选型调研

检索日期：2026-10-20。仅核对官方文档、官方演示入口和固定提交的源码；不安装依赖、不画图、不启动正式应用。当前仍为需求讨论，本文建议不代表用户已经选定组件库或视觉风格。

后续确认（同日）：调研后用户已选定 shadcn/ui＋Tailwind CSS 的方向，确认温和放松的 DeepSeek 蓝白、正文公式舒展而工具紧凑、默认浅色且可手动切深色，并确认源码及依赖边界。正式结论见 [需求总结第 0.20 节](../AI辅助学习项目需求总结.md#020-前端复用依赖与视觉方向已收口)。下文保留调研时的比较与待选状态；具体底座、版本和效果仍待验证，不表示恢复构建。

本轮用户已确认：界面组件源码由项目掌握，复杂底层能力复用锁定版本的开源库；直接同类依赖统一，间接重复经核查可以例外。用户本轮明确允许讨论视觉风格，并希望先看成熟项目的真实效果，用简单问题选择。

## 1. 结论与判断边界

**建议先让用户比较 shadcn/ui、Radix Themes、Mantine 的官方演示；工程候选优先保留 shadcn/ui＋Tailwind CSS，另以 Mantine 作完整组件库对照。** Radix Themes 可直接帮助用户比较颜色、圆角、缩放等偏好。这个排序依据本项目的源码控制、统一样式和依赖约束，不是客观审美排名。

“流行”“成熟”“看起来舒服”是不同问题。State of React 2025 调查中，MUI 的“曾使用”比例为 57.2%，shadcn/ui 为 56.1%；这证明它们在该调查受访者中有广泛使用，不能当作全球市场份额、稳定性测试或审美结论。调查还记录 shadcn/ui 的使用比例在两年内由约 20% 上升至约 56%。[调查原始结果与定义](https://2025.stateofreact.com/en-US/libraries/)

**舒适感的设计建议：**先确定阅读区和视频区清楚、导航克制、字号与间距一致，再决定色彩与装饰。Linear 2026 年的官方改版说明明确提出降低导航侧栏的视觉权重，让主内容优先，同时保留信息密度。这是成熟产品可参考的取舍，不能据此承诺所有人都喜欢相同风格。[Linear 官方改版说明，2026-03-12](https://linear.app/now/behind-the-latest-design-refresh)

## 3. 工程事实：源码控制、样式与依赖

| 方案 | 已核对事实 | 对本项目的含义（工程建议） |
| --- | --- | --- |
| shadcn/ui | 官方以可定制的组件代码作为设计系统基础；主题推荐 CSS 变量与语义 token，Tailwind 负责映射样式。[介绍](https://ui.shadcn.com/docs)、[主题](https://ui.shadcn.com/docs/theming) | 将选用的界面组件源码纳入项目；不是把底层行为库源码全部复制。上游修复需要审查合并，不能以为升级一个 npm 包就完成源码更新 |
| Radix Themes | 预设样式的包式组件库，导入其 CSS；内部为普通 CSS，公开 token。官方明确说组件相对封闭，超出 props/token 的大量覆盖可能说明选型不适合。[接入](https://www.radix-ui.com/themes/docs/overview/getting-started)、[样式边界](https://www.radix-ui.com/themes/docs/overview/styling) | 不等同于无样式的 Radix Primitives，也不等同于 shadcn。适合接受其组件结构和主题规则时单独作为主体系；不建议叠加为 shadcn 的第二套基础视觉库 |
| Mantine | `MantineProvider` 统一主题与 CSS 变量；Styles API 提供组件各部分的样式入口，核心 Button 源码使用 CSS Modules。Mantine UI 是可取用的界面示例，核心仍通过 `@mantine/core` 等包提供。[Provider](https://mantine.dev/theming/mantine-provider/)、[Styles API](https://mantine.dev/styles/styles-api/)、[UI 示例](https://ui.mantine.dev/) | 能统一外观，也能查看和维护核心源码，但不是默认逐组件复制的交付方式；选择它时应接受“项目封装源码＋锁定核心包”的维护边界，不要误称所有组件本体已在项目内 |
| Fluent UI v9 | 官方套件使用 `FluentProvider` 和 theme；固定源码的包清单依赖 Griffel 及多个 Fluent 子包。README 说明 v9 收敛套件来自对旧体系的整合。[固定 README](https://github.com/microsoft/fluentui/blob/e2642c72390b31645e5766683776199f0ab01ce2/packages/react-components/react-components/README.md) | 若采用，以 v9 为主，不无意混装旧 `@fluentui/react` 和 northstar；多个职责不同的 Fluent 子包不等于重复引入多套 UI 库 |
| Ant Design | `ConfigProvider` 提供全局与组件 token、明暗与紧凑算法；当前文档也列出 v6 的 `zeroRuntime` 模式，所以不能笼统断言所有使用必然运行时生成 CSS。[主题文档](https://ant.design/docs/react/customize-theme/) | 选择后统一走 Ant 的主题；不为聊天、截图工具又引入另一整套基础组件。Ant Design X 等扩展需单独核查实际依赖和本项目价值，不能因为“AI 组件”就默认加入 |
| Material UI | 官方默认安装使用 `@mui/material` 与 Emotion，并提供统一主题；可以更换样式引擎，但更换成本要另行核查。[安装](https://mui.com/material-ui/getting-started/installation/)、[主题](https://mui.com/material-ui/customization/theming/) | 若选择 MUI，以其主题和默认设计语言为主；不再并列引入另一套 UI 样式运行时。MUI X、模板市场等是独立范围，不能由核心库信息推导全部扩展许可或交付条件 |

**本轮最重要的依赖细节：shadcn 也不能默认“全是 Radix”。** 固定提交中已有 Base UI、Radix、React Aria 三套 registry 基础实现：Dialog 分别导入 `@base-ui/react/dialog`、`radix-ui`、`react-aria-components`。官方网站为了展示多方案，同时包含这些依赖，不代表业务应用必须安装三套。选型时应选择一套主要底座，逐组件检查来源、直接依赖与传递依赖，不把不同底座的社区组件无意拼装。[Base Dialog](https://github.com/shadcn-ui/ui/blob/ba1503c64472b82256d9de95e2e62c5901a38e8b/apps/v4/registry/bases/base/ui/dialog.tsx)、[Radix Dialog](https://github.com/shadcn-ui/ui/blob/ba1503c64472b82256d9de95e2e62c5901a38e8b/apps/v4/registry/bases/radix/ui/dialog.tsx)、[Aria Dialog](https://github.com/shadcn-ui/ui/blob/ba1503c64472b82256d9de95e2e62c5901a38e8b/apps/v4/registry/bases/aria/ui/dialog.tsx)

“源码可见”和“项目直接拥有所用组件文件”应分开记录。以上开源方案的源码可查，不意味着项目可以忽略许可证、署名或外部素材条件；正式引入时按所选版本核对，本报告不提供法律结论。

### 3.1 动效组件的适用边界

Magic UI 官方展示大量基于 React、Tailwind 与 Motion 的动效组件，并将 landing pages 作为展示场景；React Bits 提供文字动画、背景与微交互，支持按组件取源码。这些是一手产品定位，不是它们在本项目中已经通过性能或舒适度测试的证明。[Magic UI](https://magicui.design/)、[React Bits](https://reactbits.dev/)

建议主学习区保持安静，先使用基础组件已有的状态反馈；确有体验价值时才取用少量动效，并检查是否额外引入重复动画引擎。不因为“流行”默认加入整套动效集合。微软 Fluent 2 同样强调减少视觉杂乱、让用户保持专注；这是可参考的设计原则，不代表必须选用 Fluent 组件实现。[Fluent 2 设计原则](https://fluent2.microsoft.design/design-principles)

## 4. 中文长文、公式与学习场景

**事实边界：这些基础 UI 方案都不能仅凭官方组件演示，被认定已经满足本项目的数学问答、公式局部选择、PDF/PPT/Word 阅读或用户确认范围截图要求。** 本轮未运行这些流程；既有媒体、文档和公式专业库候选继续单独核查，不因选择基础组件库而更换业务协议或 Harness 执行层。

建议用同一学习场景比较，而非只看英文营销首页：一段中文说明、多行推导、一张题图、一个来源时间点、侧栏课程名、长输入草稿和大肥鱼壁纸。确认时重点检查：

1. 中文段落和数学符号能否清楚区分，行距、公式间距、长公式横向溢出是否合理。
2. 视频、资料和聊天三栏是否让正文过窄；隐藏工具或展开菜单时页面是否稳定。
3. 壁纸能否保持陪伴感而不降低题图、正文和公式对比度；不能简单以“灰色越浅越舒服”作为规则。
4. 主题能否覆盖播放器、截图编辑和文档工具栏；跨弹窗与窗口是否保持一致。

以上是后续效果验证建议，不是新增已确认功能，也不据此开始构建。

## 5. 严格控制重复依赖的落地建议

- 基础 UI 主体系只选一套；颜色、字号、间距、圆角、阴影、层级与状态集中管理。社区组件进入项目前先映射到同一套规则。
- 图标、提示、日期、表单、拖拽、Markdown/数学渲染等同类直接能力统一；只取所需组件，不复制演示站的整份 `package.json`。
- 间接依赖先区分不同职责的模块、重复版本和真正重复能力，再核对实际前端产物；包数量不能直接等同于体积或速度。
- 可兼容版本优先去重，不能强行覆盖不兼容底层库；不可避免的重复应记录来源、实际代价与保留理由。
- 本轮只核了包声明与少量组件源码，没有生产构建、bundle 分析、锁文件解析或性能测试，因此不报告体积排名和速度结论。
