# 界面设计沟通与审美训练调研

日期：2026-10-23。范围：面向没有前端设计经验的产品使用者，研究如何表达视觉偏好、比较方案、训练判断，并用于视频／资料／AI 学习工作台的设计讨论。

本文件记录研究证据与建议，不是已确认需求、实现授权或当前界面的验收结论。未运行应用、未读取真实学习视频或截图、未修改业务代码。没有通过访谈确认本项目多轮修改仍不满意的具体原因，因此以下“原因”是供核查的假设。

本轮讨论优先级已进一步明确：用户认为已有两版都存在相似问题，希望先改善第一眼观感，包括配色、字体、留白和精致程度；暂不改布局与功能。因此本轮建议以固定现有结构、控制视觉变量为主。

## 一、已阅读的来源与可支持的结论

| 来源 | 来源直接支持什么 | 不能据此认定什么 |
| --- | --- | --- |
| [NN/g：5 Principles of Visual Design in UX](https://www.nngroup.com/articles/principles-visual-design/) | 大小、视觉层级、平衡、对比与分组关系可作为分析界面的词汇；层级可由尺寸、明暗、颜色、位置、间距共同建立。 | 不能把所有审美偏好化为一个统一评分，也不能据此规定工作台必须用某种风格。 |
| [NN/g：The Aesthetic-Usability Effect](https://www.nngroup.com/articles/aesthetic-usability-effect/) | 外观会影响使用者对易用性的判断；文章记录的测试案例表明，正面视觉评价可能掩盖操作困难。应同时观察用户说了什么与做了什么。 | 好看不保证任务顺畅；功能可用也不等于用户会喜欢外观。 |
| [Design Council：The Double Diamond](https://www.designcouncil.org.uk/resources/the-double-diamond/) | 先理解并定义问题，再探索多个解法，随后小规模测试和收敛，是可采用的设计过程。 | 不能把一开始想到的解法当成已经确认的问题定义；流程本身不保证某种结果。 |
| [GOV.UK：Making prototypes](https://www.gov.uk/service-manual/design/making-prototypes) | 正式构建前可用原型探索、交流和测试；草图适合讨论基础想法，代码原型更适合逼真的交互测试。原型不等于生产实现。 | 一张漂亮截图不能证明交互有效；一个能点击的演示也不能证明正式功能、性能和安全通过。 |
| [Microsoft Fluent 2：Typography](https://fluent2.microsoft.design/typography) | 字体系统应按语义角色建立层级，兼顾可读性；官方给出分平台字阶和字体回退策略。 | 英文示例的字号与字形不能直接证明中文长段回答、公式和资料阅读舒适。 |
| [Microsoft Fluent 2：Layout](https://fluent2.microsoft.design/layout) | 间距可表达关系和重点，重复的间距模式形成节奏；提供以 4 像素为基础的间距阶梯，同时强调按具体内容灵活调整。 | “留白越多越好”不是官方结论，也没有适合所有内容的唯一网格或栏宽。 |

以上来源是设计机构自身的方法／研究解读、政府服务手册和设计系统所有者的官方指导。它们适合建立讨论框架，不构成对“某种训练能在几周内提高审美”或“某种提示必然让模型产出满意界面”的实验性证明。

## 二、为什么反复说“更高级、更简洁”可能难以收敛

以下是分析建议，尚未确认本项目分别存在这些问题。

1. **词语没有对应到可观察的变化。** “清爽”可能指颜色少、边界少、内容少、间距大、工具默认收起，也可能指重点更突出。同一个词可以导向相反的设计。需要把感受翻译为区域、现象、目标和保留项。
2. **问题层级与修改层级不一致。** 如果不满集中在字体关系和表面质感，重做布局或添加功能可能绕过当前问题。本轮应先固定结构，分别核查配色、字阶、间距、边界和控件几何；只有用户之后指出结构问题，再讨论布局。
3. **参照物的用途不同。** 营销首页的留白和视觉冲击不一定适合长时间学习工作台；空页面展示不出长文件名、长回答、公式、选中内容和错误状态的效果。参考时应优先找相似任务和相似内容负荷。
4. **每轮同时改变太多。** 布局、字号、颜色、卡片样式同时变化后，即使更喜欢新版本，也很难知道改善来自哪里，下一轮又可能破坏有效部分。
5. **“满意”没有在同一条件下比较。** 不同窗口、缩放、内容和状态会干扰判断。只看最新一版容易忘记上一版具体好在哪里。
6. **不同内容状态会改变观感。** 文件很少、聊天为空时显得干净，不代表长文件名、长回答和公式出现时也协调。当前先保持三栏和交互不变，用同一组合成学习内容比较视觉效果。

这些假设对应一个实用流程：先把不满定位清楚，再比较多个方向，最后固定方向精修。它是对[双钻过程](https://www.designcouncil.org.uk/resources/the-double-diamond/)在本项目上的应用建议。

## 三、没有设计背景，也能把“感觉”说具体

不要求用户先学会 CSS 或准确报像素。用户提供任务和偏好，设计者负责解释可选办法、补齐合理默认与提出取舍。

### 1. 用五句话代替一个抽象形容词

| 要说明的内容 | 示例，均为假设 |
| --- | --- |
| 在什么情况下 | 我一边听课，一边对照 PDF，偶尔向 AI 提问。 |
| 哪个区域让人不舒服 | 顶部和三个面板的工具条。 |
| 看到了什么 | 按钮都很亮，标题和正文差不多大，不知道先看哪里。 |
| 想出现什么效果 | 第一眼先看见视频或资料内容，工具需要时容易找到。 |
| 哪些东西要保留 | 播放、截图、当前对话入口保持容易操作；不要靠隐藏全部工具来减少杂乱。 |

可复用格式：**“当我做〔任务〕时，〔区域〕出现〔具体问题〕；我希望〔可观察结果〕，同时保留〔重要内容／操作〕。”**

### 2. 把常见形容词拆成可讨论的维度

| 原始表达 | 应继续澄清的可观察维度 | 可尝试的设计方向，非既定方案 |
| --- | --- | --- |
| 太乱 | 同时抢注意的区域数量、按钮权重、分组是否清楚 | 减少竞争重点，统一弱化次要操作，按任务分组 |
| 太空 | 单屏有效内容、面板宽度、间距是否缺乏用途 | 收紧不必要间距，给主要内容更多面积 |
| 不高级 | 字体层级是否稳定、对齐是否一致、颜色／边框是否过多 | 统一字阶、间距、图标和表面层级，再讨论风格 |
| 太像管理后台 | 表单／卡片占比、内容是否被外壳挤压 | 减少外壳，让视频、文档和回答成为主体 |
| 太像玩具 | 饱和色、装饰、圆角、动效和图标语气 | 探索更克制的颜色及装饰，保留明确反馈 |
| 不舒服 | 字小、行距、对比、长行、拥挤或视觉疲劳 | 逐项比较阅读设置，避免直接归因为某种主题 |

这些维度借用了[视觉层级的分析词汇](https://www.nngroup.com/articles/principles-visual-design/)，但表中的方向是本次提出的讨论办法。没有必要把“高级”等主观词禁用；应要求设计者解释它在当前页面上具体意味着什么。

### 3. 描述参考时标注“借用范围”

每张参考只回答三件事：喜欢哪个区域、喜欢它的什么关系、哪些部分不适用。例如：“借用它安静的工具条和清楚的文字层级；三栏比例沿用本项目学习任务；不借用首页大标题和装饰插画。”

负面参考同样有用：“这个页面虽然简洁，但常用按钮需要打开两级菜单，我不想要这种取舍。”参考是具体证据，不能只提供产品名并要求整体模仿。

## 四、固定三栏结构，低成本探索视觉方向

以下为建议流程，不构成当前阶段的实施计划。

1. **选一个代表性场景。** 例如“听课时对照资料，并读取已有 AI 解释”。使用合成视频占位、虚构文件名和合成回答即可比较视觉效果；不需要读取用户真实素材。
2. **固定比较条件。** 同一窗口、缩放、内容和面板状态。主屏尺寸应来自用户实际设备；尺寸未知时先声明样例尺寸，不把它当最终适配要求。
3. **先做两到三个视觉方向。** 保留三栏结构、栏宽、功能、文案和内容，用不同但内部统一的字体、表面与颜色关系表达方向；标出每版刻意改变的内容。这个数量用于控制讨论成本，不是研究规定。判断精细差异时保持相同明暗主题，避免把主题偏好误当成细节改进。
4. **选定方向后分轮收敛。** 建议依次处理配色与表面层次、字体层级、间距密度、边框／圆角／图标。顺序可按最明显的问题调整；每轮保留上一轮确认的规则。
5. **做单问题比较。** 如果不确定问题来自密度，就保持颜色、栏宽、字体不变，只改变间距／行高等一组相关设置。更准确的说法是“每轮只解决一个问题”，而非机械限制只能改一个 CSS 属性。
6. **记录保留项和淘汰理由。** 例如“保留 B 的文字层级；淘汰 B 的强边框；下一轮只统一控件圆角”。形成一页视觉简报，写明颜色角色、文字角色、间距阶梯、控件几何和反面示例，避免每轮重新发散。
7. **用可运行页面检查视觉与行为。** 静态方向选定后，用长内容、选中、悬浮、焦点、加载和错误状态检查样式完整性，确认现有操作仍然可用。此次不借机增加功能。原型探索与生产实现分别记录，其依据是[GOV.UK 的原型指导](https://www.gov.uk/service-manual/design/making-prototypes)。

可用于学习工作台的比较维度：

| 维度 | 要比较的问题 |
| --- | --- |
| 内容优先级 | 第一眼看到的是学习内容，还是工具外壳？当前主任务是否清楚？ |
| 配色与表面 | 文字与背景是否舒适？三栏、工具条和输入区是否有清楚但不过重的层次？ |
| 字体与密度 | 长中文、公式、文件名和时间戳能否区分层级？缩小空隙是否损害阅读？ |
| 控件权重 | 常用操作是否顺手？低频操作是否抢占与内容相同的视觉权重？ |
| 控件几何 | 输入框、按钮、标签、卡片的圆角与边界是否出自同一规则？差异是否有明确用途？ |
| 一致性 | 相同级别的标题、按钮、菜单、边界和间距是否采用相同规则？ |

字阶和间距可以从成熟系统取合理起点，再用中文学习内容验证。例如可参考 [Fluent 的字体角色](https://fluent2.microsoft.design/typography)与[间距阶梯](https://fluent2.microsoft.design/layout)，但本研究不建议现在就更换组件库，也不把官方示例字号直接定为本项目标准。

## 五、审美如何练习：把“见过”变成“能解释”

以下是可尝试的四周练习安排，不是已验证有效的课程，也不保证在固定期限达到某种水平。目标是提高比较、说明和自我判断能力，而不是先变成职业设计师。

| 阶段 | 每次约 10—15 分钟可做什么 | 留下的产物 |
| --- | --- | --- |
| 第一周：学会拆解 | 每次选两个相似任务的真实界面，比较第一视觉重点、文字层级、分组、间距与工具位置；不急着评“高级”。 | 一张标注过的对照图，写出 3 条具体差异 |
| 第二周：形成偏好 | 从已有对照中挑出喜欢与不喜欢的部分；尝试说出原因和代价，如“更安静，但入口更隐蔽”。 | 一页偏好词典，含喜欢、反感、可接受取舍 |
| 第三周：小范围模仿 | 只重做一个工具条、文件列表或回答块；保持内容不变，分别探索字体、间距、边界。可用草图，无需编程。 | 同一局部的两至三种可比较版本 |
| 第四周：回到项目 | 用同一学习任务比较原界面和一个候选；先说视觉偏好，再实际完成任务，记录不一致处。 | 一页设计简报和一次修改记录 |

具体做法建议：

- 收藏要有注释，少量高相关参考比无说明的大量收藏更利于当前讨论。先收相似工作台、阅读器和编辑器，再看纯视觉展示。
- 先遮掉品牌、配色或装饰，观察布局和字阶是否仍然清楚；也可以把两张图缩小查看视觉重心。这是分析练习，不是验收方法。
- 每次必须写“我更喜欢哪一版、具体哪里、代价是什么”。允许偏好变化，保留当时的任务条件。
- 不要求所有人品味一致。可以同时保留“结构是否清楚”的分析和“我更喜欢哪种气质”的个人判断。
- 请设计者解释选择并提出两种有意义的替代，而不是让用户独自决定几十项字体、圆角和像素参数。

## 六、视觉验收与交互验收应分别进行

| 评价层 | 怎么看 | 可以证明什么 | 不能代替什么 |
| --- | --- | --- | --- |
| 视觉方向 | 同内容、同尺寸的截图／静态稿并排比较 | 用户更喜欢哪种外观，层级与密度是否符合方向 | 连续操作、键盘、滚动、性能 |
| 交互原型 | 完成代表性任务，观察寻找、误触、重复操作和打断 | 在原型条件下流程是否容易理解和完成 | 真实后端、模型与生产状态 |
| 正式功能 | 确定性测试、浏览器验证和相关真实链路验证 | 被实际执行的契约与行为是否符合要求 | 用户是否喜欢、长期学习是否舒服 |
| 实际学习体验 | 用户在确认素材范围内完成真实学习片段，给出分层反馈 | 对本人任务与偏好的适配情况 | 尚未测试的场景或其他用户群 |

把评分拆为两句：“外观我偏好 B”“操作时我在 B 的截图入口停顿了”。不要让其中一句替代另一句。此区分与[NN/g 对审美可用性效应的测试观察](https://www.nngroup.com/articles/aesthetic-usability-effect/)一致。

本轮用户已明确：浏览器版与 Harness 桌面版都有类似问题；当前优先改善第一眼观感，包括配色、字体、留白和精致程度。此前参考 Codex／Harness，只是因为它们相对顺眼，尚未找到理想参照。因此下一步应从发现视觉偏好开始，不能把任一参考当成用户已经认可的最终审美目标。设计者应先给完整合理默认并解释差异，不要求用户从零决定几十个像素参数。

## 七、本项目现场核对与适用边界

本节来自当前工作区文件和已有合成截图的只读核对，不是对正在运行的用户窗口进行验收。核对前已查看 Git 工作区；存在大量进行中的修改，本轮不覆盖它们。

- [前端方案](../../docs/architecture/前端方案.md)和[前端开发规范](../../docs/architecture/前端开发规范.md)记录了从蓝白、参考 Codex 到复用 Harness 原生界面的多轮演变；最新方向保留左课程／中资料／右 AI，统一主要 UI 字体和 14px，精简常驻工具。历史记录表明换过参照，不能仅据此认定多轮不满意的确切原因。
- [桌面说明](../../desktop/README.md)、`desktop/client/learning.css`、`desktop/client/course-library.css` 与锁文件表明，桌面以固定 Harness 客户端及其主题为底座，并有本项目的学习区适配；旧浏览器前端另有 React／Tailwind／Base UI 实现。更换视觉方向不必自动扩展为更换框架、重建聊天或扩大功能阶段。
- [精简界面验证记录](../reports/harness-desktop/桌面精简界面与交互验证-2026-10-22.md)明确区分技术验证和用户主观认可。已有通过项不能代替用户对视觉的评价。
- [PDF／字幕／知识库需求收口](../../docs/product/PDF阅读与字幕及课程知识库需求收口-2026-10-22.md)仍是单独的需求边界；本次视觉讨论不启动其中尚未实现的功能。

本次实际查看了 `output/playwright/desktop-minimal-release-20261022-r1/` 的 `light-1440.png`、`dark-1440.png` 和 `draft-preserved.png`。这些是 2026-10-22 的合成内容截图，不代表当前实时界面；空聊天与文件页不足以评价有长回答和数学公式时的学习效果。

| 截图中可观察到的现象 | 可讨论的视觉问题 | 判断边界 |
| --- | --- | --- |
| 左树较紧凑，文件网格较疏，中右区域大面积使用相近背景 | 全页疏密节奏、表面层次和重点是否符合偏好 | 留白本身不是错误，空聊不能代表有内容时的效果 |
| 课程、文件、页签与对话标题采用相近字号 | 同一字体体系内，能否用字重、明暗和分组建立层级 | 不据此擅自推翻已确认字号；统一字体不意味着所有角色必须相同 |
| 输入框较圆，其他工具区多为直线与较小圆角 | 控件形状差异是否有明确层级和整体规则 | 不同用途可以有不同圆角，不能单凭差异判错 |

以上属于讨论线索，不是已经证实的故障。建议先固定现有三栏和内容，比较视觉方向；只有后续证据指向空间结构问题时，再单独讨论布局。

官方能力说明不保证自动理解尚未明确的个人偏好。建议将发现方向、定稿样板、实现与核对分为不同交付物，以下不是已确认实施计划。

1. **发现方向。** 设计者整理少量相关产品的实际工作界面，说明每张图适合观察什么。用户只需指出更喜欢的局部及感受；未找到理想参照时，不要求先提交完整设计稿。
2. **形成简报。** 以一个主要方向为基础，明确背景／表面／文字／强调色的角色、字体角色、间距节奏、控件形状和图标规则。可参考多个局部，但应由设计者统一，避免机械拼贴。
3. **比较同场景样板。** 探索阶段可比较两到三种内部一致的方案；精修阶段每轮处理一类主要问题。使用相同合成内容、窗口、缩放和状态，保留上一轮认可的部分。
4. **确认后落实。** 将认可的简报与基准截图关联到现有前端规范；正式实现沿用当前组件和业务边界。不建立互相冲突的设计真相源，不以新 Skill 的默认审美覆盖已确认规则。
5. **核对实际结果。** 浏览器截图与实际 Electron／Windows 字体、缩放效果分别核对；在相同视口和显示比例下列出差异。合成内容的核对不需要读取真实视频、补帧或扩大截图范围。

可复用的反馈句式：

> 保留 B 的〔具体部分〕；〔某区域〕仍让我觉得〔感受〕，因为〔观察到的现象〕。这一轮只探索〔目标〕，保留其他已认可部分。请用同样内容并排展示修改前后，并解释关键取舍。

例子：

> 保留 B 的背景和输入框。目录文字与正文一样抢眼，我希望目录更安静，同时仍容易辨认。请先比较两种导航文字层级，不改变栏宽和回答样式。

[Linear 的 2026-03-12 官方改版说明](https://linear.app/now/behind-the-latest-design-refresh)提供侧栏、标签和边界的前后对照。其做法包括降低导航视觉权重、调整图标、柔化分隔，并在实际产品内反复比较。它适合学习如何通过一组小而一致的变化提升精致程度，不代表用户应喜欢或复制 Linear。
