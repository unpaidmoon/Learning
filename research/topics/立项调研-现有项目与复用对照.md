# 立项调研：现有项目与可复用能力对照

调研日期：2026-10-19（Asia/Shanghai）。证据范围：官方文档、发布记录、许可文件、当前源码与 npm registry。未安装或运行以下产品，未下载模型、抽取视频画面、上传用户文件或发送付费模型请求。

## 1. 结论与既定路线

**保留 Windows Harness 执行层＋完全定制 React UI＋后期安卓独立基础学习的路线。** 本轮没有找到可直接证明完整满足「原地引用长视频 → 用户主动截图、缩放平移裁剪 → 图文解题 → 必要字幕 → 再必要时课程知识库」的现成产品闭环。

这不是说这些产品不存在某项相关能力，而是不能把「能上传视频」「能读取 YouTube 文稿」「能聊天」组合推断成已经实现了上述交互。比较的价值在于少重复开发成熟模块、统一学习入口，而非再部署一套完整聊天产品与 Harness 并行争夺会话和模型编排。

优先参考的内容为：

1. **SurfSense Local**：音频分窗、时间轴产物、检查点、图文附件和本地检索模块设计。
2. **AnythingLLM**：附件、来源侧栏、资料处理适配；其独立移动端可参考本地数据和模型 Provider 分层。
3. **Open Notebook**：Notebook/Source 组织、资料处理状态和上下文预算，但其现有聊天不是截图问答的直接实现。
4. **Open WebUI**：文件处理 API、解析引擎适配、引用和检索流程；不搬整块聊天 middleware。
5. **Buzz**：字幕导出、字幕与播放联动、取消后子进程清理；ASR 继续优先用底层引擎接口，而非导入 Qt 应用队列。

以上是工程判断，未承诺减少多少开发天数、内存或 token。用户已有的 Windows 首版范围、禁止 AI 自动补图、后台体验优先和统一业务 schema 均不改变。

## 4. 精确复用切面与集成代价

代价分级是静态判断：低＝边界较小的格式/纯展示逻辑；中＝需映射数据、配置和生命周期；高＝需接入完整数据库、权限、agent 或前端宿主。没有运行原型，不给开发工时承诺。

建议：首版参考小范围附件和引用交互；安卓阶段再研究其独立数据路线。不要把它作为额外常驻 RAG 平台接入，以免两套会话、身份和执行编排相互映射。

### 4.4 SurfSense Local：最接近本地后台结构，但不能误读成现成视频学习

事实：当前受支持的 Local 是独立 `surfsense_local` 树，组合 FastAPI、SQLite、Huey、Vite React 和 Electron。旧 hosted 的 PostgreSQL/Next.js/LangGraph 架构不能直接混作当前桌面实现。[官方架构决定](https://github.com/MODSetter/SurfSense/blob/176aed261a24a85d217538960e91c59746561bd2/docs/adr/0004-desktop-app-is-its-own-tree.md)

当前上传白名单没有 MP4，只接文档、图片和部分音频；文档还注明音频暂无预览。它具备字幕相关的处理产物，不代表本地视频播放器和提问链已存在。[storage.py](https://github.com/MODSetter/SurfSense/blob/176aed261a24a85d217538960e91c59746561bd2/surfsense_local/backend/modules/documents/storage.py)、[文件与音频架构](https://github.com/MODSetter/SurfSense/blob/176aed261a24a85d217538960e91c59746561bd2/docs/architecture/documents.md)

### 4.5 Buzz：字幕体验与进程清理，避免整套 Qt 依赖

## 6. 复用收益应怎样落到本项目

建议形成明确的复用登记，优先采取以下方式：

| 层次 | 本轮建议 | 避免的重复与新增成本 |
| --- | --- | --- |
| 视频/截图/公式 | 直接依赖播放器、裁剪和 Markdown/KaTeX 底层组件 | 减少重复交互实现；仍需自己连成最短截图提问流程 |
| 字幕产物与后台状态 | 参考 SurfSense 的时间轴、检查点；借鉴 Buzz 格式和清理案例 | 复用成熟模式；任务 ID、来源版本、优先级和 GPU 所有权保持项目统一 |
| 文档解析 | 借鉴 AnythingLLM/Open WebUI 的适配切面，直接使用已选底层解析库 | 避免搬整套 collector、鉴权、数据库或另一套 agent |
| 课程和引用 | 参考 Notebook/Workspace/Source 的组织、候选选择、来源卡片 | 增加课程、题号、页码、跨页原题和视频时间定位，不只做文本 chunk 列表 |
| 安卓独立 | 参考 AnythingLLM Mobile 的本地存储、Provider 和平台适配边界 | 不照搬 React Native UI、GPL 代码或单向导入协议作为本项目同步 |
| Harness | 仍是 Windows 执行与工具层 | 这些项目不替代 Harness；提取逻辑经学习工具接口接入，不嵌第二套循环编排 |

对每个候选模块记录：固定源版本、具体文件、许可、可独立的边界、移植依赖、业务映射、取消/恢复行为、性能与 token 影响、升级责任。整套服务 API 接起来容易，不代表部署、数据复制、两套配置和升级成本更低。

## 7. 本轮未验证与下一步最小检查

未验证：五个产品的实际 Windows 安装、界面操作数、字幕准确率、数学公式效果、模型调用与用量、长视频内存、电脑关机后的安卓行为，以及任何真实源代码移植量。本报告不声称替代项目已在本机运行。

进入实现前，建议只做与首版闭环直接相关的验证：

1. 保持一条播放器内用户截图→编辑→提问的路径，核对确认图和来源时间，不自动补图。
2. 从 SurfSense 音频产物设计中抽出一个与库无关的 Segment/Checkpoint 契约，与本项目 GPU worker 对齐；不安装整套产品。
3. 取一个附件/引用组件设计做小范围适配，测是否真正减少操作和耦合，而非先搬整套聊天 UI。
4. 对截图信息充分的用例，检查没有字幕/检索/标题/摘要的隐藏调用；业务上下文仍由既定 Harness 学习流程控制。
5. 资料阶段再验证完整题目、中文短词、页码题号与引用定位。不能因为竞品有 RAG 就认为考研数学题检索已经解决。
6. 安卓阶段再以设备本地存储、电脑关机后直接问答与恢复同步验收；不把响应式 Web、浏览器直连或配对导入当完整多端协同。

本轮结论是选择性复用和设计借鉴的优先顺序，不新增首版功能，也不改变已确认的产品目标。
