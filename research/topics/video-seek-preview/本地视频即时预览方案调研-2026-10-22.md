# 本地视频即时预览方案调研

日期：2026-10-22。性质：围绕用户反馈的方案研究，不是实施授权、兼容验收或性能承诺。本轮未修改应用代码、契约、计划或测试，未安装依赖，未读取或抽取用户视频画面，也未执行真实素材性能测试。

用户已明确：接受鼠标位置附近的预览帧；要求鼠标悬停时迅速出现图片，不接受先只显示时间或“正在预览”。“附近”允许的最大时间偏差尚未量化。其余三个反馈（原生课程目录窗口置前、空对话不重复创建、取消独立条件／更正功能）不在本报告范围。

## 1. 调研结论

建议把悬停路径改成“已准备并解码的小图片 → 按时间索引定位 → 显示图集区域”，将视频解码移到悬停之前。低分辨率、稀疏采样、图集、提前解码分别优化不同环节，应组合使用。Shaka 官方支持独立 WebVTT 图片／图集缩略图，证明这属于成熟播放器已有的实现方式；本项目无需为此替换整个播放器。[Shaka 官方 README](https://github.com/shaka-project/shaka-player#thumbnails-support)

B 站一手接口实际返回了图集 URL、每格尺寸、网格尺寸和时间索引（见第 2 节），可以解释为何它不需要在每次悬停时临时精确解码原视频。但接口存在本身不能证明播放器何时预取，也不能证明任何网络、任何视频下都没有等待。

只缩小 CSS、把 `preload` 改成 `auto`、长期保留隐藏 `video`、换用 `fastSeek()`，均不能单独证明能满足首次任意位置立即有图。对于从未处理的本地视频，缩略图仍需读取和生成；要达到上述体验，必须提前做准备，并实测首次准备与前台播放的资源竞争。把加载文字删掉、保留错误位置旧画面或只显示时间，均不能视为需求达成。

## 2. B 站一手接口实证

主研究者于本日通过无登录 HTTP 请求读取 B 站 JSON 元数据；未下载返回的图片，未使用用户视频。以下是有限样本观察，接口没有稳定性承诺，不建议本地应用依赖此接口。

| 请求 | 返回与图集结构 | 时间索引观察 |
| --- | --- | --- |
| [`videoshot?bvid=BV1NF411J7Jf&index=1`](https://api.bilibili.com/x/player/videoshot?bvid=BV1NF411J7Jf&index=1) | HTTP 200、`code=0`；10×10 网格；每格 480×270；1 个图集 URL | 12 项；`[0,0,6,12,18,24,30,36,42,48,54,60]` |
| [`videoshot?bvid=BV1GJ411x7h7&index=1`](https://api.bilibili.com/x/player/videoshot?bvid=BV1GJ411x7h7&index=1) | HTTP 200、`code=0`；10×10 网格；每格 160×90；1 个图集 URL | 33 项；起始 `[0,0,5,11,17,23,29,34,39,46,53,61,67,72,78]`；末尾 `[180,186,193,201,211]` |
| [`videoshot?bvid=BV1oy4y1z7Uu&index=1`](https://api.bilibili.com/x/player/videoshot?bvid=BV1oy4y1z7Uu&index=1) | HTTP 200、`code=0`；10×10 网格；每格 160×90；1 个图集 URL | 11 项 |

接口显示：采样不必是精确逐帧；不同视频的每格尺寸也不固定。这个样本不支持把 B 站概括成“固定每秒一张 160×90 图片”。尚未核实当前播放器预取时机、首次悬停请求序列或实际悬停延迟；这些不能从 JSON 倒推出性能数字。

另通过项目固定 Playwright CLI 与隔离 Chromium 观察公开页面 `BV1NF411J7Jf`：页面 HTTP 200，在未悬停、主动阻止 `media` 类型请求的条件下，DOMContentLoaded 后观察 8 秒，未记录到匹配 `videoshot` 的请求。该条件可能影响播放器初始化，结果只能记为“本次未观察到”，不能据此证明或否定正常播放时的预取。此观察不是悬停速度测试。原始记录保存在忽略的 `output/playwright/bilibili-preview-research-observed-20261022/observation.json`；所属浏览器已关闭，进程组清理结果 `remaining_pids=[]`，未使用用户登录状态。第一次采集因 `run-code` 控制台输出未进入结果而没有可用观察摘要，保留其 CLI 记录，不计为成功实证。

## 3. 当前代码事实

只读检查的主要位置是 [SeekPreview.tsx](../../../frontend/src/media/SeekPreview.tsx)、[SeekPreview.css](../../../frontend/src/media/SeekPreview.css)、[media.py](../../../backend/src/learning_app/media.py) 和 [应用契约](../../../docs/architecture/应用契约.md)。

- `SeekPreview` 仅在 `visible` 时挂载解码器；隐藏时删除 `src` 并 `load()` 释放。再次悬停会重新创建。
- 预览 `video` 指向原视频版本路由，`preload="metadata"`；目标变化后修改 `currentTime`。在途保留一个 seek，完成后追最新目标。
- 只有目标与已解码时间差小于 0.06 秒才显示视频，否则隐藏并显示“正在预览…”。这是精确时间匹配，和用户现在接受邻近帧的取舍不同。
- CSS 的 160×90 是显示框；当前没有独立生成 160×90 媒体的流程。
- 正式前后台依赖清单和锁文件本次未发现 FFmpeg／WebCodecs demuxer 的项目固定交付闭包。系统命令搜索能找到 WinGet 链接下的 `ffmpeg.exe`／`ffprobe.exe`，这不等于项目已固定、可随应用交付。

以上是实现事实，尚不是已测出的性能归因。MDN 说明 `metadata` 仅建议预取元数据，`preload` 整体只是浏览器提示；它不承诺随机位置的帧已解码。[MDN preload](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/preload)

## 4. 提速方法分别解决什么

| 方法 | 能减少的工作 | 不能解决的边界 |
| --- | --- | --- |
| 实际生成低分辨率图片 | 后续读取、图片解码、驻留像素量 | 首次仍要取得源视频帧；不能把 CSS 缩小当成源解码降采样 |
| 放宽到邻近采样帧 | 减少需要准备和切换的帧数 | 需约定时间误差，不能以整片首帧替代任意位置 |
| 小型分块图集 | 减少大量独立小文件和逐张切换请求 | 一张超大图集会增加首次解码与内存，仍须分块预算 |
| 在进入播放器前读取、解码图片 | 把图片加载／解码移出悬停交互路径 | 冷缓存必须先生成，不能让 `decode()` 凭空创造图片 |
| 保留预览解码器、合并最新请求 | 避免反复建立视频解码器及排队陈旧目标 | 原视频随机 seek 与帧依赖仍存在，并增加资源驻留 |
| 低清独立视频代理 | 提前付出转码成本，后续读取与解码较轻 | 代理生成、存储和随机 seek 成本仍在，静态预览通常无需整条代理 |

FFmpeg 固定标签 n8.0 的官方文档源码包含 `scale`（修改输出尺寸）、`fps`（丢／补帧至指定输出帧率）、`tile`（拼接连续帧）；同一文件直接示范关键帧转 128×72、8×8 图集。`thumbnail` 则分析一批帧选代表帧，会持有该批数据；不应因为名字符合就默认采用。[FFmpeg n8.0 filters.texi](https://raw.githubusercontent.com/FFmpeg/FFmpeg/n8.0/doc/filters.texi)

CSS 展示尺寸与媒体自然尺寸是不同概念，`videoWidth` 表达媒体本身的宽度。下采样应发生在生成缓存图片时，而不是只改 `<video>` 样式。[MDN videoWidth](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/videoWidth)

图片 `decode()` 的 Promise 在图片已解码、可安全插入 DOM 时完成，可用于提前准备即将显示的图集。悬停时只在已准备好的图片上切区域，才把图片解码也移出关键路径。[MDN HTMLImageElement.decode](https://developer.mozilla.org/en-US/docs/Web/API/HTMLImageElement/decode)

## 5. 候选路线与取舍

| 路线 | 适合程度 | 依据与限制 |
| --- | --- | --- |
| 预生成低分辨率分块图集＋实际时间索引 | 推荐作为主体 | 已有成熟播放器路径；悬停无需 seek。需提前生成并预解码当前使用的块。采样密度与尺寸须测试后固定 |
| 优先关键帧建立稀疏覆盖，再补密 | 候选加速手段 | FFmpeg 支持跳过非关键帧；但关键帧间隔属于源视频，不能保证 1～2 秒邻近精度，也不能保证所有编码器同样高效 |
| 按输入 seek 分批抽帧 | 候选生成策略 | 可避免为单点从头顺序解码，但要比较多次 seek 和扫描成本，不能盲目每张起一个进程 |
| 全片顺序 `fps` 抽帧 | 候选生成策略 | 实现直观；滤镜处理已解码帧，低输出帧率不等于源视频无需顺序解码，长课冷启动须实测 |
| 保活隐藏 video＋`fastSeek()` | 补充实验，不作为即时保证 | 能减少重新建立开销、以精度换速度；MDN 标注 `fastSeek()` 兼容性有限，仍不是缓存图片读取 |
| WebCodecs＋Worker＋demuxer | 当前不优先 | 可控程度高，但新增容器解析、编码配置、资源生命周期和兼容工作；没有消除冷启动取帧与帧依赖 |
| 转成低清／全关键帧代理视频 | 当前不优先 | 可能有利于持续拖动动态画面，但本需求允许静态邻近图，更简单的图片路径更易限定成本 |

FFmpeg `skip_frame=nokey` 支持只保留关键帧；`-ss` 的输入定位通常先到目标前的可定位点，精确转码还会解码并丢弃到目标间的片段。源编码、GOP、索引和磁盘速度会影响实际收益；不能仅根据选项名称承诺耗时。[FFmpeg codec options](https://ffmpeg.org/ffmpeg-codecs.html#Codec-Options)、[FFmpeg main options](https://ffmpeg.org/ffmpeg.html#Main-options)

`fastSeek()` 以精度换速度且浏览器支持有限；`requestVideoFrameCallback()` 提供已送往合成器的帧回调，用于确认呈现时机，不负责提前生成整条时间轴。[MDN fastSeek](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/fastSeek)、[MDN requestVideoFrameCallback](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback)

WebCodecs 不自带视频文件的 demux，仍需另一个库提取编码块；配置支持需要探测。规范要求解码器在需要关键块时接收关键帧，并要求及时释放不用的 `VideoFrame`，否则可能阻塞。这些都不是“换 API 即瞬时”的保证。[MDN WebCodecs API](https://developer.mozilla.org/en-US/docs/Web/API/WebCodecs_API)、[W3C WebCodecs](https://www.w3.org/TR/webcodecs/#videodecoder-interface)

## 6. 推荐设计草案，尚未授权实施

1. 在课程资料发现／导入后的本地准备阶段排入缩略图任务，提前处理将要观看的视频。当前视频优先，其他资料串行或受控并发；问答、截图与播放优先。只读原件，不复制整课视频，不使用模型。
2. 先比较关键帧扫描、输入 seek 稀疏抽样、顺序低帧率抽样三种生成策略，再固定主路径；不要在未测量时声称其中某一种必然最快。
3. 独立保存实际帧时间和图集区域，不用等间隔假设冒充真实时间；保留长宽比。160×90、240×135 以及不同采样密度只作为测试候选。16:9 的一小时视频按每两秒一张得到 1800 张；按每像素 RGBA 四字节计算，160×90 合计 103,680,000 字节、约 98.9 MiB，240×135 约 222.5 MiB。160×90 小图组成的 10×10 图集为 1600×900，单页约 5.5 MiB。以上是原始像素算术示例，不是实测内存，也不是磁盘压缩大小；实际浏览器／GPU 还可能有其他开销。故建议全轴压缩产物提前生成，已解码图集仅有限驻留，不将全片解码图片无预算常驻。
4. 用 `asset_id`、`source_version`、采样／尺寸参数和生成器版本形成缓存身份；先写临时产物，完整校验再发布清单，旧版本绝不套到新视频。任务去重，检查点持久，取消后只处理所属任务／进程。
5. 播放器读取可用清单，将“预取压缩图片字节”和“解码为可呈现像素”分别管理：提前读取必要图集块只省去读取等待，还需解码才能移出呈现路径。鼠标变化只查索引和切图片位置；跨块时应提前准备邻块，过期回调按来源版本和世代隔离。若全轴解码超预算，可评估有限已解码图集缓存或覆盖全轴的小尺寸粗图常驻，但粗图时间偏差仍须符合用户最终约定，不能自行把几十秒偏差当成“附近”。主视频仍然松开才跳转一次。
6. 缩略图属于本地可重建播放缓存，不能进入附件、学习工具、模型输入快照或自动检索。缓存路由只接受受限业务身份和版本，不暴露任意本地路径。该边界沿用现有[应用契约](../../../docs/architecture/应用契约.md)。
7. 清理仅作用于明确可重建缓存，不删除原视频、已提交截图、对话或用户资料；失败保留可重试状态，不伪装即时预览已就绪。

## 7. 首次无缓存的真实约束

用户已经拒绝“先仅时间，再出现图”的方案，本报告不把它作为默认降级。上面的设计重点是把工作提前做，而不是继续要求用户接受悬停等待。

但对刚加入且从未处理的长视频，若用户立即指向任意时间，同时又要求此前完全没有读取／预处理开销，就不能从现有来源得到“必定立即有对应图”的保证。应先用合成且授权的素材测出提前准备的成本，再讨论准备时机和可见行为；不能把遥远旧帧、静默无预览或挡住播放器的准备页算作用户已经接受的方案。

尚需用户决策的是允许何时开始本地准备（课程加入后自动处理、仅处理当前／即将打开的视频等），以及邻近帧可接受的时间偏差。参数和实现手段应由测量支持，不应把本轮研究建议自动写成已决定需求。

## 8. 后续验证建议

先用确定性合成视频覆盖短片／长片、不同源分辨率和 GOP、可变帧率、旋转与宽高比、版本变更、损坏与缺失文件。真实素材仅在确认范围内使用，不为测试读取额外用户画面。

分别记录：冷缓存首次打开到全轴满足约定误差的时间；热缓存首次悬停到真实图片呈现；连续快速移动与跨图集块的图片延迟；生成期间播放掉帧／问答影响；CPU、磁盘读量、缓存字节、驻留像素和取消释放。首帧、占位符、时间标签不能冒充预览图出现；一次成功不能冒充 p95。

本轮证据分层：官方文档／源码已查；B 站有限接口元数据样本已观察；本地现状仅做只读代码检查。原视频取帧性能、浏览器预取与绘制实测、正式 FFmpeg 版本与闭包、用户实际学习体验均未覆盖，不更新既有验收状态。
