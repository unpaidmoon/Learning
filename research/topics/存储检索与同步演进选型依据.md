# 存储、资料检索与同步演进：技术选型依据

> 当前适用性补充（2026-10-20）：自动找题、专用题目目录/原题组装及历史备份产品建议已失效，知识库必要但用途继续待细化；BGE/向量等仅保留候选，不能由旧找题方案推出必建。自有数据/来源版本/工程迁移可恢复仍有效。当前工作包见[MVP](../../docs/plans/MVP开发计划.md)，V2故障恢复、V7导出导入/离线/目录迁移分别验，当前未执行。

核对日期：2026-10-18。本文基于已确认需求和官方资料，区分选型建议、已执行的小样本检查与待验证事项。未安装模型、上传资料、抽取视频画面或修改用户原始资料。

## 1. 推荐结论

采用 **SQLite＋SQLAlchemy 2＋Alembic＋应用托管文件目录**。业务数据与检索索引分开建模，原始视频和文档原地引用。知识检索分为结构化定位、中文关键词检索与语义召回三种能力，通过一个检索接口组合；首个视频截图问答闭环不等待全量资料解析和索引。

| 领域 | 推荐 | 定位 |
| --- | --- | --- |
| 业务存储 | SQLite，验证通过后启用 WAL | 课程、资料目录、聊天、字幕、任务、学习记录 |
| 数据访问与迁移 | SQLAlchemy 2＋Alembic，API 数据模型独立 | 明确事务和仓储边界，避免数据库模型直接成为接口协议 |
| 中文关键词 | jieba 搜索模式＋数学词典预分词＋FTS5 | 提供可控中文召回；页码、题号仍走结构化字段 |
| 语义检索 | BGE-small-zh-v1.5 CPU 基线＋可替换向量存储 | 资料找题阶段实现，处理换一种说法找题，不能被关键词替代 |
| 向量索引 | sqlite-vec 为本地候选，需通过 Windows 和重建测试 | 不引入独立向量服务；预 v1 依赖隔离为可重建索引 |
| 文件观察 | watchfiles＋启动/恢复时目录对账 | 事件防抖、文件稳定后处理、增量更新 |
| PDF | PDF.js 阅读，pypdfium2 后台页面与文本层 | 页面定位与渲染、原生文字提取 |
| 扫描文档与结构 | Docling 作为受控后台适配器候选 | OCR、版面、题目与公式处理需用真实数学资料验证 |
| Office | LibreOffice 独立进程转换，保留原件 | 缓存 PDF 预览；支持旧 DOC/PPT 的兼容路径 |
| 后续同步 | 应用级增量记录协议，业务冲突自动合并 | 首版保留 ID、版本和本地路径隔离；不提前实现完整同步引擎 |

以上是项目设计选择，不是官方性能保证。下文说明依据和准入检查。

## 2. SQLite 可用，但必须验证实际运行时

业务数据规模取决于资料文字量、聊天和索引，不等同于几十 GB 原始视频。视频本身不放进数据库，因此当前无需部署 PostgreSQL、Redis 或独立向量数据库服务。

WAL 支持读写并行，但仍只有一个写者，且要求访问数据库的进程位于同一台主机；不能通过 Tailscale/共享盘让多台设备直接打开同一个数据库文件。各端应有各自的数据库，通过应用协议同步。[SQLite WAL 官方说明](https://sqlite.org/wal.html)

2026 年官方披露 WAL-reset 问题：3.7.0 到 3.51.2 受影响，3.51.3 及之后修复；官方列出 3.44.6 和 3.50.7 回移修复版本。不能只固定 ORM 或 Python 主次版本就认定已修复。[官方修复发布说明](https://www.sqlite.org/releaselog/3_51_3.html)

### 2.1 已执行的本机最小检查

2026-10-18 在内存数据库中执行，没有创建项目数据库：

- 当前 PATH 中 Python：3.12.5。
- 此 Python 的 `sqlite3.sqlite_version`：3.45.3。
- FTS5 与 trigram 可创建并查询。
- **当前运行时不应作为正式 WAL 运行环境。** 此结论不代表用户其他 Python 环境的版本。

### 2.2 可执行的运行时准入策略

1. 创建项目独立运行环境，记录 Python 补丁版本、发行来源、平台和实际 `sqlite3.sqlite_version`；检查实际 SQLite 源版本/供应商修复信息。
2. 默认准入 SQLite 3.51.3 或更新的经过验证版本；如使用旧支线，必须确认所选补丁版本包含官方回移修复。版本固定在项目环境清单中。
3. 环境验证脚本实际创建临时数据库，确认 WAL、FTS5、中文测试与备份恢复；不能把“安装某个 Python 版本”当成这项检查已经通过。
4. 若所选 Python 发行包捆绑的 SQLite 不合格，更换经过验证的 Python/SQLite 运行时发行组合；不在系统 Python 中手工替换未知 DLL，也不假设 `pysqlite3-binary` 在 Windows 有合适构建。
5. 暂时无法取得合适运行时时，可用 DELETE journal、主进程串行数据库访问完成开发验证，但应接受读写相互阻塞，并明确这不是已通过的 WAL 方案。

应用运行后也检查实际加载的 SQLite 版本，避免打包或用户环境变化导致回退。

### 2.3 进程与事务

主应用持有数据库写入边界；转写、PDF 渲染和解析 worker 通过结果/进度消息回报，避免每个 worker 任意写数据库。事务保持短小，不在事务中等待模型接口或大文件处理。字幕纠错结果以 `base_revision` 条件更新，旧任务不能覆盖用户后续编辑。

开启外键约束、设置有限 busy timeout，并检查 PRAGMA 的返回结果。写入频率按批次控制；播放进度不逐帧写入。用户资料与聊天优先采用充分的持久化配置，索引吞吐通过批次与调度优化，而非默认牺牲业务数据持久性。[SQLite PRAGMA 文档](https://www.sqlite.org/pragma.html)

备份使用 SQLite backup API 或受控快照流程，不在运行时仅复制一个 `.db` 文件。SQLite 提供在线备份机制，Python 标准库也暴露 `Connection.backup()`。[SQLite Backup API](https://sqlite.org/backup.html)、[Python sqlite3 备份文档](https://docs.python.org/3/library/sqlite3.html#sqlite3.Connection.backup)

## 3. 数据访问：SQLAlchemy，不额外叠加 SQLModel

推荐 SQLAlchemy 2 的明确表模型和事务边界，常规 CRUD 可用 ORM，FTS5 和专用索引使用参数化 SQL。API 请求与返回使用独立的 Pydantic 模型，数据库实体不直接暴露给前端。迁移由 Alembic 管理；SQLite 某些修改需要建立新表并迁移数据，Alembic 有专门的 batch 模式。[SQLAlchemy SQLite 方言](https://docs.sqlalchemy.org/en/20/dialects/sqlite.html)、[Alembic SQLite 批迁移](https://alembic.sqlalchemy.org/en/latest/batch.html)

SQLModel 建立在 SQLAlchemy 与 Pydantic 上，本身是合理组件；本项目包含字幕版本、资源身份、任务状态和后续同步，接口模型和持久化模型会独立演进，因此不把合并两类模型作为主要收益。暂不增加这一层。[SQLModel 官方说明](https://sqlmodel.tiangolo.com/)

直接使用 `sqlite3` 可以更少依赖，但不会自动解决迁移、事务和并发；不把省一层轻量访问代码误当成显著性能优势。选型性能判断以后端实测为准。

## 4. 原始文件、派生文件与稳定引用

### 4.1 文件不由路径充当身份

建议拆分以下概念：

- `asset_id`：稳定资料 ID，聊天与来源引用使用它。
- `source_version`：某次原始内容版本，用内容哈希最终确认。
- `asset_location`：某设备上的绝对路径、目录根 ID、相对路径及可用状态。
- `artifact`：字幕、截图、解析结果、缩略图、预览 PDF、索引等派生产物。
- `locator`：某个版本中的页码、页面区域、视频时间或字幕片段。

第一次导入先读取目录、大小、修改时间和必要媒体元信息，尽快可用；在后台以有界 I/O 计算内容哈希。大小和修改时间只能发现候选变化，不能证明两个文件内容完全相同。移动后先尝试目录映射和候选匹配，哈希确认后保留 `asset_id`，避免聊天来源全部失效。

派生文件键包含来源版本、处理器版本和配置哈希。内容没变不重复处理；字幕修正只更新对应片段及相关索引。重复引用同一原件不复制整段视频，多个聊天引用同一截图时也不重复写二进制内容。

### 4.2 应用数据目录

用户可选择应用数据根目录。数据库、截图、字幕和解析产物使用该目录内的相对路径；原始资料保留外部路径映射。不把视频、整份 PDF 或大量截图 BLOB 塞进业务表。

建议目录职责：`db/` 业务数据库；`objects/` 内容寻址的截图等资产；`derived/` 可重建的解析/预览/索引；`exports/` 用户导出；`tmp/` 可清理临时产物。原图与裁剪图分开引用，发送给模型的图仍以用户实际选择为准。

### 4.3 自动目录跟踪

推荐 watchfiles。其官方支持 Windows 二进制包，提供递归目录监听、防抖和轮询回退。[watchfiles 文档](https://watchfiles.helpmanual.io/)、[watch API](https://watchfiles.helpmanual.io/api/watch/)

目录事件仅作为“可能变化”的信号：批量复制/下载未完成时等待稳定，按资料 ID 合并任务；应用启动、恢复或监听异常后做目录对账。Windows 原生目录通知可能发生缓冲区溢出，需要枚举目录恢复状态，不能只靠事件永久保证完整。[ReadDirectoryChangesW 官方限制](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-readdirectorychangesw)

## 5. 检索：结构化定位＋中文关键词＋语义召回

### 5.1 三类需求分别处理

| 用户请求 | 优先路径 | 结果 |
| --- | --- | --- |
| “某讲义第 35 页第 6 题” | 文件名/别名、章节、页码、题号字段 | 精确来源与完整题目，而非相似文字块 |
| “老师刚才说的洛必达法则” | 当前视频时间范围＋字幕关键词 | 有时间戳的相关片段 |
| “那道第一象限区域旋转成几何体的题” | 关键词与语义并行召回、结构约束与课程优先排序 | 题目候选，保留公式、图形和原页位置 |

资料中的题目应建立题目级单元，包含小问和图形；必要时跨页关联。字幕单元按时间和句段组织。不能把每一页等长切块后，就声称已完成题号定位与数学题完整性支持。

### 5.2 默认 FTS5 不等于中文检索

`unicode61` 会把连续的字母/数字类字符视作一个词，不会自动进行中文词语切分。trigram 支持子串，但少于三个 Unicode 字符的 MATCH 不返回结果，直接依赖它会遗漏“积分”“极限”“导数”这类短词。[FTS5 tokenizer 官方文档](https://sqlite.org/fts5.html#tokenizers)

已在本机内存库验证：

| 索引文本与 tokenizer | 查“积分” | 查“定积分” |
| --- | --- | --- |
| 原文“计算定积分的方法”，unicode61 | 0 | 0 |
| 同一原文，trigram | 0 | 1 |
| 预分词“计算 定积分 积分 的 方法”，unicode61 | 1 | 1 |

此表只证明分词边界问题，不是整体中文检索准确率或速度测试。

推荐 jieba 搜索模式，增加数学术语和课程词典；查询与文档使用相同处理版本，把词语用空格分隔后交给 FTS5。jieba 官方提供搜索模式、用户词典和原文 token 位置，采用 MIT 许可。[jieba 官方仓库](https://github.com/fxsjy/jieba)

原文与分词字段分别保存；高亮要映射回原文，不能把 FTS 分词文本直接当成正确原文位置。题号/公式/页码不依赖分词。少量短子串可在课程/文件过滤后做受限精确匹配；若后续发现必要，再测 bigram 或额外索引，避免一次建立多套低价值索引。

### 5.3 保留语义能力，按资料检索阶段接入

关键词无法充分处理同义表达和用户只记得题意的情况。语义检索是已确认资料问答需求的一部分，不能因截图问答优先就将它永久取消。

建议以 **BAAI/bge-small-zh-v1.5** 做本地中文语义基线：官方模型卡标注 MIT、512 维和约 24M 参数；准确率需在数学题意、术语和公式语料上单独验证，不把通用基准当作考研数学效果结论。[模型发布方说明](https://huggingface.co/BAAI/bge-small-zh-v1.5)

先用 Sentence Transformers 显式设置 CPU 建立基线，限制线程和小批量；必要时比较 ONNX CPU。其官方支持 ONNX 后端，但转换、池化、归一化与量化都需要保持一致并验证，不能默认转换后更快或结果完全相同。[Sentence Transformers 推理优化](https://www.sbert.net/docs/sentence_transformer/usage/efficiency.html)

向量存储以 sqlite-vec 为本地候选，避免首版部署额外数据库服务器。该项目支持 Windows，明确仍为预 v1，存在兼容变化；因此必须固定版本，并隔离成可丢弃重建的索引，不承载业务事实。[sqlite-vec 官方仓库](https://github.com/asg017/sqlite-vec)

若扩展的 Windows 打包/兼容验证不通过，小规模语义原型可把向量存为普通数据并用 NumPy 精确相似度作为基线；不宣称该回退可无限扩展。按实际文本块数量、过滤能力、延迟与内存决定是否保留或更换。几十 GB 视频不能直接推导向量规模。

检索流程为结构过滤＋关键词/语义候选融合＋去重＋题目/段落组装＋有限结果输入。初期不用生成模型为每个候选打分；如果效果确有缺口，再比较独立 reranker 的收益和成本。索引版本包含嵌入模型 revision、维度、分词器及解析器版本，模型切换不混用不同向量空间。

### 5.4 上下文与检索索引边界

知识库默认索引教材、习题、有效字幕等学习资料。聊天、截图和解答以会话归档，用户提及旧题时在对应会话范围取回；播放位置、计时与日统计使用结构化查询，不进入向量库。

聊天历史长期完整保留；模型输入由上下文模块组装，保存 `conversation_id`、相关消息/图片引用和来源 locator。先保留当前题目的原始图片、条件和推导，再裁剪无关旧历史；只有明确阈值触发摘要或旧题检索，不每次重新调用模型总结全部历史。

## 6. 文档解析与原文阅读

推荐把“阅读/渲染”“已有文字提取”“OCR/公式/版面识别”视作不同能力，分别通过适配器提供。

| 组件 | 用途与官方依据 | 限制与项目决定 |
| --- | --- | --- |
| PDF.js | 浏览器解析、渲染与阅读器；Apache-2.0。[入门](https://mozilla.github.io/pdf.js/getting_started/)、[许可](https://github.com/mozilla/pdf.js/blob/master/LICENSE) | 扫描页能显示不代表已经 OCR；通过本地 HTTP 提供资源。用于阅读器、页序与原页定位 |
| pypdfium2 | PDFium Python 绑定，渲染及文本层提取；本体 Apache-2.0/BSD-3-Clause。[官方仓库](https://github.com/pypdfium2-team/pypdfium2) | 分发要带 PDFium/第三方 notices；PDFium 非线程安全，放入受控进程或串行调用，不能任意并发线程。[API 警告](https://pypdfium2.readthedocs.io/en/stable/python_api.html) |
| Docling | PDF/图片/Office 的结构化处理，OCR 与可选公式提取；代码 MIT。[官方仓库](https://github.com/docling-project/docling)、[公式示例](https://docling-project.github.io/docling/_generated/examples/code_formula_granite_docling/) | 模型许可分别核对；中文扫描题目、公式、跨页边界、坐标需样本验证。作为后台适配器，按需加载，不常驻占用全部 GPU |
| LibreOffice | 无头转换及 Office 兼容；MPL-2.0。[启动参数](https://help.libreoffice.org/latest/en-US/text/shared/guide/start_parameters.html)、[许可](https://www.libreoffice.org/licenses/) | 保留原文件，转换 PDF 为预览缓存；可能受字体和格式影响，独立 user profile 防止与用户实例争用 |
| PyMuPDF | 提取、渲染、OCR 集成。[官方许可](https://pymupdf.io/licensing)、[OCR 说明](https://pymupdf.readthedocs.io/en/latest/recipes-ocr.html) | AGPL/商业许可双路线，不作为默认宽松许可依赖；OCR 另依赖 Tesseract。若采用需明确相应许可策略 |

当前 Docling 官方格式表已列旧 DOC/PPT，并注明需要 LibreOffice；不能沿用“只支持 DOCX/PPTX”的旧结论。DOCX/PPTX 原生结构和经 PDF 转换的阅读结构，需要各自关联来源。[官方格式表](https://docling-project.github.io/docling/usage/supported_formats/)

普通文字提取不能保证得到可检索的 LaTeX，也不能保证完整还原上下标、分式、积分上下限或图形。保留页面及区域引用，检索找到题目后取完整题目区域和必要原文；公式结构化识别失败时仍可回看原页，但不能声称已经支持准确的公式语义检索。

印刷页码与 PDF 页序分字段保存，不默认二者相同；印刷页码尚未识别时明确采用 PDF 页序。Office 转换版本变更可能改变页码，旧引用绑定来源/预览版本，不能无声跳到错误页面。

## 7. 后续安卓与同步：保留边界，不提前建设通用平台

### 7.1 首版需要保留的基础

- 全局稳定的实体 ID、资料版本、设备来源和修改版本。
- 本地文件路径与共享实体分离；共享记录不以 `D:\\...` 路径作为资源身份。
- 所有业务写入经过明确服务接口，后续能在同一事务里写同步 outbox。
- 新消息/附件各自有 ID，重复提交可以幂等去重。
- 软删除/墓碑与有限恢复历史的结构边界，后续离线设备不能把删除内容复活。

首版不需要运行同步服务器、CRDT 文档库、完整跨端操作日志或多套数据库，只需要避免把数据和接口锁死在本机路径/内存状态上。

### 7.2 不直接同步数据库文件

后续各端持有本地副本，通过 mutation ID、游标、outbox/inbox、确认与重试同步变化。聊天消息和附件按唯一 ID 合并；相同记录/字段修改按明确版本排序取胜。大文件走按需下载、内容校验和本地可用状态，索引可在设备重建或下载适配版本，不默认复制整份索引库。

电脑在线时承担实时协作中心；电脑关机后安卓端独立使用，之后补传。Tailscale 只连接设备，不替应用实现这些合并与重试规则。

### 7.3 LWW 必须定义“新”

不能用上传到达时间，也不能仅用设备墙钟。后续建议评估 HLC（混合逻辑时钟）与稳定设备 ID 的确定性排序，先保留 revision 字段，完整算法在同步阶段实现。HLC 能维护已观察因果关系并容忍常见时钟回拨，但不能判断任意断网设备上两个并发修改在现实中谁更晚；这仍需要确定性的胜出规则。[HLC 原始论文](https://cse.buffalo.edu/tech-reports/2014-04.pdf)

共同组织问题时，草稿文字块和附件集合分开存储，避免手机输入文字覆盖平板刚添加的图片。并发修改同一文字块可以自动取胜，附件按 ID 合并；发送通过幂等键完成一次状态转换，防止多端重复发起收费问答。以上是后续应用协议设计，不要求首版实现。

### 7.4 Dexie、PGlite、Automerge 的位置

| 候选 | 官方能力 | 本项目决定 |
| --- | --- | --- |
| Dexie | IndexedDB 的 JS 包装层。[官方文档](https://dexie.org/docs) | 若安卓采用离线 Web/PWA，可用于本地聊天/草稿；不是自动跨设备同步引擎，Windows 端不必提前引入第二份业务真相库 |
| PGlite | 浏览器内的 PostgreSQL/WASM，可持久化到 IndexedDB。[官方文档](https://pglite.dev/docs/) | 当前没有必须在浏览器执行 PostgreSQL SQL 的需求，不为未来可能性引入额外数据库引擎 |
| Automerge | local-first 协同数据类型和同步相关能力。[官方文档](https://automerge.org/docs/hello/) | 当前用户接受自动 LWW，首版不必引入完整 CRDT；若未来真实多人逐字协作需求出现再评估 |

安卓客户端形式仍需在对应阶段选择。浏览器存储受配额、清理策略和 origin 隔离约束；大视频离线、后台恢复和凭据保存需在真实安卓设备验证，不能仅靠选了 IndexedDB 就承诺稳定长期离线。[浏览器存储限制](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

## 8. 学习资产导出与迁移接口

建议 `export_bundle(scope, include_originals=false)` 输出版本化目录/ZIP：

- `manifest.json`：格式版本、应用版本、导出时间、实体清单、内容哈希。
- JSONL：课程、资料关联、聊天、消息、字幕有效版本与必要修订、学习明细/汇总。
- 标准文件：字幕优先提供 VTT/SRT，聊天可额外导出 Markdown；图片为原格式。
- 来源映射：逻辑资料 ID、内容版本、原路径提示、原目录相对路径；不导出密钥。
- 原文件默认外部引用，用户选择时包含；索引/缩略图等可重建内容默认不导出。

`import_bundle()` 先校验 manifest 与内容哈希，再做版本迁移和幂等导入；`relink_roots()` 一次映射旧资料根目录到新位置。导入后重建检索，不依赖数据库私有表结构长期兼容。在线备份与资产导出分开提供：前者用于恢复运行状态，后者用于迁移和通用读取。

建议最小接口边界：

```text
AssetCatalog: register / resolve / relink / fingerprint
ArtifactStore: put / open / retain / collect_unreferenced
DocumentParser: inspect / parse / read_location
RetrievalService: locate / search / get_context
ConversationStore: append / read_window / resolve_references
AssetTransfer: export_bundle / import_bundle / relink_roots
ChangeFeed: publish_committed_change（首版只定义稳定写入边界）
```

## 9. 实施顺序与必要验证

### A. Windows 视频截图问答闭环

实现业务数据库、资料身份、原地引用、截图/裁剪资产、连续会话、来源时间点、持久任务和恢复。当前视频字幕可按时间范围查询；图片与文字完整时不触发检索，不等待索引完成。

准入检查：修复后的 SQLite 运行时；一次写入故障恢复；截图与聊天导出恢复；文件移动后来源可重新定位；后台任务不拖慢播放和截图。

### B. 本地资料知识库

加入 PDF 阅读/文本层与 Office 预览，扫描页按需 OCR；实现章节/题号/页码定位、中文关键词和语义混合召回、原题完整组装和原文跳转。交付自然语言找题前，必须加入题意改写类测试，而非只测文件名和题号。

必要样例：两字词“积分/极限/导数”；同题号多讲义；印刷页码偏移；跨页题干；含图题；公式符号与上下限；扫描讲义；DOC/PPT 字体与分页；字幕修正只生效一次且不重复检索初稿。

测量检索覆盖、候选正确率、完整题干率、来源跳转准确率、时延、内存、CPU/GPU 与模型输入 token。处理尚未完成与已处理但未命中必须在结果状态中区分。

### C. 安卓独立学习与协同

评估本地客户端存储和大文件缓存，之后实现应用级同步、时钟偏差/离线重试/LWW、共同草稿与幂等发送。先测电脑中心方案，Tailscale 直连/中继下分别测文件与视频流。此阶段不影响 Windows 首版核心验收。

本文完成的是选型依据和一个内存 FTS 边界检查；尚未完成任何文档解析、向量模型、同步性能或真实数学资料准确率验证。
