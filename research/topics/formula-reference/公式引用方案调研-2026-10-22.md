# 对话公式引用方案调研

日期：2026-10-22。本文件记录候选方案的官方资料、固定源码与隔离探针证据；属于研究建议，不代表正式实施、验收或需求变更。正式功能和依赖尚未修改。只使用合成公式，没有读取用户课程、聊天或屏幕，没有增加模型调用。

## 结论与推荐方案

**建议把公式引用改成“不可变来源 + 结构化选区 + 片段展示”，停止把“能截出一段连续、可独立渲染的原始 LaTeX”作为所有引用的必要条件。交互引擎优先验证 MathLive 只读 mathfield；不能直接用它的默认选区序列化替换现有函数。**

上一轮讨论中“保留 KaTeX、补完整 AST 映射”只是候选。核查后，KaTeX 并没有现成的稳定结构选择 Interface；如果继续该路线，项目仍需承担解析来源跟踪、排版节点关联、命中测试和片段导出。相比之下，MathLive 已有公式位置、命中测试、只读选择等能力，适合优先复用，但矩阵、跨结构范围和混合文字仍需项目处理。此处推荐的是技术验证优先级，尚未把引擎迁移记为已决定或已验收。

本次建议有三个明确边界：

- 用户仍按“鼠标划选 → 临时添加入口 → 可移除引用卡片 → 补问题并发送”的流程使用，不引入默认模型 OCR、规划或额外模型请求。
- 保留精确选区约束。不能把补全括号、分母、底数或矩阵其他单元格当作提高成功率的方法。结构吸附若改变范围，不能悄悄沿用；需要严格选区策略或由用户明确重新选择。
- 不承诺任意二维划选都能变成完整数学表达式。完整表达式与不完整片段分开表示；不能准确表达的片段提供明确的手动选区图片入口，不自动截图或补入整式。

## 当前实现的具体问题

审查基线为项目锁定的 `katex@0.16.22`、`react-markdown@10.1.0`、`rehype-katex@7.0.1`；工作区开始时无已跟踪改动。源码摘要见[本次来源记录](../../../output/playwright/formula-reference-research-20261022/source-evidence.json)。

1. [selection.ts](../../../frontend/src/chat/selection.ts) 解析部分 KaTeX 叶节点位置，插入带 nonce 的 HTML 数据标记，再从浏览器 Range 反推源码；命名算符另外与词法 token 对账。此方式已经做了来源保护，但缺少统一的公式选择模型。
2. 同一文件将多个已选节点压成最小起点与最大终点，并检查中间映射节点是否跳选；局部公式最终还要重新通过 KaTeX 渲染。它把“原始来源连续性”“实际可见选择”“是否独立完整”耦合到一个判定中。
3. [MarkdownAnswer.tsx](../../../frontend/src/chat/MarkdownAnswer.tsx) 在 `selectionchange` 时执行上述判定，因此用户尚未点击添加就出现 `FORMULA_SELECTION_UNMAPPED`。多个不同失败原因最终显示同一个提示。
4. [drafts.py](../../../backend/src/learning_app/drafts.py) 的 `DraftReference` 与来源校验同样以单个原始 UTF-16 范围及精确字符串为中心。只改前端映射会在草稿保存或正式发送时重新遇到契约不匹配。

KaTeX 固定版本源码明确把 `__parse` 与内部渲染树标为不建议公开使用且结构可能变化。其公开渲染 Interface 不提供现成的公式选区提取能力；根式等结构由排版 Implementation 生成，不能只靠文本节点还原全部可见结构。继续使用内部能力需要固定版本并集中封装，不能把“读取 AST”本身视为完整解决方案。[固定 KaTeX 入口源码](https://github.com/KaTeX/KaTeX/blob/v0.16.22/katex.js)、[固定根式 Implementation](https://github.com/KaTeX/KaTeX/blob/v0.16.22/src/functions/sqrt.js)、[公开渲染文档](https://katex.org/docs/api)

## 路线对比

| 路线 | 能复用的能力 | 本项目仍要承担的部分 | 建议 |
| --- | --- | --- | --- |
| 继续给当前叶节点映射补特例 | 当前代码与来源范围校验 | 新符号、嵌套、宏、视觉顺序及所有结构片段 | 不作为主线；仅处理独立且明确的维护问题 |
| 深改 KaTeX，建立渲染来源映射 | 现有版式、原生文字混合选择 | 自建命中、完整来源跟踪、结构树导出；维护固定源码补丁 | 可行备选，不能宣称成本最低 |
| MathLive 只读结构交互 + 项目引用 Module | 公式位置、命中测试、结构选区与部分序列化 | 严格范围、混合选择、矩阵片段、来源校验 | **优先做最小纵向验证** |
| MathJax 4 的结构 DOM / `data-latex` | 丰富结构与节点级 LaTeX 表示 | 拖选、精确来源、片段导出及交互协调 | 备选；非直接替换方案 |
| 全部变成选区图片 | 保留用户确认后的视觉效果 | 图片确认、像素范围、附件生命周期；失去结构文本 | 仅作为明确选择的备用方式 |

这不是“所有公式可以不测试”。改进在于按少量结构规则组合处理，而不是按每条公式的写法不断增加分支；仍须验证嵌套、选区边界和来源不扩大。

## 候选引擎：MathLive

### 官方能力与适用范围

MathLive 官方明确区分静态公式和只读 mathfield：静态标记中的浏览器选区不等于 LaTeX 选区，局部选取可能出现意外；需要选区能力时建议使用 `<math-field read-only>`。这与本项目目前从静态 KaTeX DOM 反推源码的困难直接相关。[官方静态公式指南](https://mathlive.io/mathfield/guides/static/)

公开 Interface 提供 `selection-change`、`selection`、`getValue(range, format)`，发行类型还包含 `getValue(selection, format)`。`Selection` 可携带多个 range，官方以矩阵列说明不连续选区；offset 表示公式内部的插入位置，**不是原始 LaTeX 或 Markdown 的 UTF-16 下标**。[官方 API](https://mathlive.io/mathfield/api/)、[固定制品类型](../../../output/playwright/formula-reference-research-20261022/vendor/package/types/mathfield-element.d.ts)

本次实际研究制品为 **mathlive@0.111.0**，npm 包的 `gitHead` 为 `b8c11c9c13935ca58f10971977bd5d8060746118`，SHA-512 integrity 为 `sha512-jOcmftawnJgFerkOxKk8aVZeOxL9qgX/kF2D9+AOL5MpNYWYllXpkzDs1uSWJEUAOZhJuq86jzL18/1j0oOLWg==`。主研究探针已下载固定 tarball 并核对 integrity；不以官网版本文字或 GitHub 的 latest release 代替实际制品。此版本无普通 npm dependencies，未因此给正式项目增加 Compute Engine。[固定 npm 元数据](https://registry.npmjs.org/mathlive/0.111.0)、[对应源码树](https://github.com/arnog/mathlive/tree/b8c11c9c13935ca58f10971977bd5d8060746118)

### 结构选区仍有明确限制

固定源码中，鼠标移动通过 `extendSelectionTo()` 更新选区，部分类型的所有子节点进入范围后，会把父结构也纳入。`getValue(selection, 'latex')` 则把各 range 的已选 Atom 序列化，再由 `joinLatex` 合并。**结构选择比字符猜测成熟，但默认扩选策略和序列化结果不能直接当作本项目的精确引用事实。**[固定 Model Implementation](https://github.com/arnog/mathlive/blob/b8c11c9c13935ca58f10971977bd5d8060746118/src/editor-model/model-private.ts)

鼠标处理自行执行命中测试、pointer capture 和 `preventDefault()`。Mathfield 使用 Shadow DOM，公开事件也有重定向规则；它的公式内部选区与外部普通文字的 DOM Selection 是两套状态。需要统一的消息选区协调 Module，不能在用户选择外部文字时顺便读取 mathfield 遗留的 selection。[固定指针 Implementation](https://github.com/arnog/mathlive/blob/b8c11c9c13935ca58f10971977bd5d8060746118/src/editor-mathfield/pointer-input.ts)、[固定 MathfieldElement Implementation](https://github.com/arnog/mathlive/blob/b8c11c9c13935ca58f10971977bd5d8060746118/src/public/mathfield-element.ts)

`latex` 输出保留宏表达，`latex-expanded` 展开宏，`latex-unstyled` 去除部分样式；这些是结构的序列化格式，不能据此推断字节级保留原始输入。Compute Engine 的数学规范化更可能改变顺序和表示，不应拿数学等价作为“选中了同一段原文”的证据。本项目的引用不需要求值引擎。[输出格式说明](https://mathlive.io/mathfield/api/#outputformat)、[官方交互与规范化说明](https://mathlive.io/mathfield/guides/interacting/)

### 固定 Chromium 探针观察

主研究执行的结果位于 [隔离探针 result.json](../../../output/playwright/formula-reference-research-20261022/result.json)。它验证候选本身的行为，尚未接入正式草稿、后端或模型。以下是实际观察，不是普遍兼容保证：

| 合成操作 | 实际提取结果／行为 | 对方案的含义 |
| --- | --- | --- |
| `det` 等式链局部拖选 | `\det M=\det A\det` | 能处理现有实现曾漏标记的命名算符；空白未按原字节保留 |
| 分式只选分子 | `a+b` | 原生结构选区可以直接得到子式 |
| 从分子 `a` 拖到分母 `d` | 扩成整个分式 | 必须明确显示最终范围；不能在后续序列化时静默补全 |
| 矩阵首行 `1` 到 `2` | `12` | 丢失单元格关系；不能直接作为完整矩阵引用 |
| 矩阵 `1` 到 `4` | `1234` | 需要项目的矩阵片段表示或显式整式选择 |
| 下标 `i` 到上标 `2` | `_{i}^2` | 是片段，不能强制每个结果都是独立完整公式 |
| 外部前文跨公式拖到后文 | 原生选区仅含“前文后文”，mathfield 保留旧选区 | 必须统一协调，避免漏引公式或加入旧选区 |

探针所有样例的原内容均保持未修改。它证明 MathLive 有更直接的公式选择基础，也证明“替换渲染器后直接调用 getValue 就完成改造”不成立。

### 可以复用的公开选择原语与尚缺能力

固定版本公开提供 `getOffsetFromPoint(x, y, {bias})`，可以将指针坐标转成公式位置；`getElementInfo(offset)` 提供部分元素的 LaTeX、深度与几何信息。项目因此不必从可见字符串猜测第几个 `det`，但这些信息没有直接给出本项目需要的完整父子分支、矩阵单元格身份及原始源码范围。[官方选择 Interface](https://mathlive.io/mathfield/api/#mathfieldelementgetoffsetfrompoint)、[固定发行类型](../../../output/playwright/formula-reference-research-20261022/vendor/package/types/mathfield-element.d.ts)

还实际核查了 SSR 能力：固定包可以在 Node 中将 LaTeX 转成 MathML；分式和矩阵结构得以保留。但两个合成输入使用 `convertLatexToMathMl(latex, {generateID:true})` 均未生成 `extid`，静态 HTML 也未包含 mathfield 的 `data-atom-id`。因此不能仅凭该选项的文档描述，假设服务端、静态输出与浏览器交互节点已经具备共同稳定身份。正式落地前必须验证同一套纯解析／投影 Implementation，必要时只在固定引擎 Adapter 内维护窄范围扩展；不能把独立重解析的随机 ID 直接持久化。[官方转换 Interface](https://mathlive.io/mathfield/api/#convertlatextomathml)、[固定 SSR 类型](../../../output/playwright/formula-reference-research-20261022/vendor/package/types/mathlive-ssr.d.ts)、[实际 SSR 输出](../../../output/playwright/formula-reference-research-20261022/ssr-result.json)

### 安全与交付约束

官方说明 Mathfield 会生成动态样式，并提供 `createHTML` 接入 Trusted Types／清洗；部分 LaTeX 命令能够产生 HTML 属性或链接。项目若引入该引擎，须独立验证现有 CSP、外链及 HTML 命令限制、资源本地交付和只读不变性，不能沿用 KaTeX 的 `trust:false` 名称假设策略相同。[MathLive 官方安全说明](https://mathlive.io/mathfield/guides/security/)

## 候选引擎：MathJax 4

### 可复用的节点级来源信息

固定考察 **MathJax-src 4.1.3**。MathJax v4 的 TeX input 会把 `data-latex` 加到内部 MathML 节点，并带到 CHTML／SVG 输出；4.1.3 包含 UTF-8 属性处理修复。这使它具备比“只有整式 annotation”更细的来源表示，但不等于具备任意拖选后精确提取原文的现成 Interface。[官方 v4.0 发布记录](https://github.com/mathjax/MathJax-src/releases/tag/4.0.0)、[官方 4.1.3 发布记录](https://github.com/mathjax/MathJax-src/releases/tag/4.1.3)

固定 `TexParser.updateResult()` 读取当前 parser 字符串片段并 trim，上下标通过子节点属性组合，花括号内容也可能重建、补分隔空格；源码还注明生成排版的部分环境有限制。因此 `data-latex` 是**节点级 LaTeX 表示／溯源线索，不是不可变原始消息的 source map**。没有原始范围或稳定节点身份时，不应靠 `indexOf(data-latex)` 匹配重复符号、宏展开和相同子式。[固定 TexParser Implementation](https://github.com/mathjax/MathJax-src/blob/4.1.3/ts/input/tex/TexParser.ts#L606)

整式 MathItem 的原始输入仍可保存，TeX input 在根节点附上整份输入；可用它把一个公式节点锚定到项目消息，再以项目拥有的稳定结构路径定位片段。但“构建并校验这些路径”属于需要实现和验证的设计，官方资料没有替本项目完成它。[固定 TeX input Implementation](https://github.com/mathjax/MathJax-src/blob/4.1.3/ts/input/tex.ts#L186)

### Explorer 和菜单不等于本项目引用

官方 Explorer 支持按语义树导航、朗读、放大及高亮子式，适合辅助阅读。菜单中的 `copyOriginal()` 则复制 `mathItem.math.trim()`，即当前整式原始输入；并非任意鼠标拖选片段。没有发现与 MathLive `selection/getValue(selection)` 等价、可直接满足本项目混合选区和范围确认的公开 Interface。此结论仅限本次核查的官方文档及固定代码，不是对所有扩展的不存在证明。[Explorer 官方说明](https://docs.mathjax.org/en/v4.0/basic/explorer-commands.html)、[固定菜单 Implementation](https://github.com/mathjax/MathJax-src/blob/4.1.3/ts/ui/menu/Menu.ts#L1733)

### 适用判断

MathJax 可以作为“保留较丰富 TeX 排版能力、在 DOM 中获取结构级 LaTeX 表示”的备选，但仍需项目实现选区协调、结构片段表示、消息身份绑定和后端校验。

本次另下载并校验 `mathjax@4.1.3` 与 `@mathjax/mathjax-newcm-font@4.1.3`，在隔离 Chromium 中核查三个合成公式的 CHTML。实际存在分式、符号和矩阵等结构，以及节点级 `data-latex`；一次矩阵输出的环境层属性为 `{pmatrix}`，并非整个原始矩阵源码。整式根节点保留完整源码，不能据此推断每层都有可独立还原的原始片段。

浏览器宽范围鼠标探测出现不一致的原生选区结果；该探针没有实现自己的命中／高亮协调，也未完成全部辅助交互设置隔离，因此不据此判定“MathJax 无法选择”或计算通过率。它只验证了排版和结构元数据实际存在，未验证生产级局部引用。首次探针漏挂转换输出样式，已保留为驱动失败记录，补样式后复核版式，不把首次结果当产品缺陷。证据见[MathJax 观察](../../../output/playwright/formula-reference-research-20261022/mathjax-result.json)、[最终版式](../../../output/playwright/formula-reference-research-20261022/mathjax-formulas.png)。

若只为局部选择能力而整体换成 MathJax，收益尚不足以抵消这部分自建工作。字体和按需数据必须本地固定交付；官方说明 v4 字体默认可来自 CDN，本次字体请求实际全部指向隔离本机服务器。[官方 CHTML 字体配置](https://docs.mathjax.org/en/latest/options/output/chtml.html)

## 引擎调研的初步取舍

1. MathLive 只读 mathfield 是优先值得继续验证的结构选择 Adapter，但**不是可直接替换的完整引用 Module**。探针已揭示矩阵、跨分支扩选和跨文字公式的缺口。
2. MathJax 4 的节点 `data-latex` 可降低部分来源表示成本，仍缺统一选区与不可变原文锚点，不能承诺换库解决。
3. 无论选哪个引擎，项目的持久化和校验都应区分：不可变来源身份、用户实际确认的范围、选中片段、用于展示的序列化。不能把它们重新压回“一个可独立渲染的连续源码字符串”。
4. 任一引擎都不能通过默默补选分母、整矩阵、宏其他展开内容来提高成功率。若引擎进行了结构吸附／扩选，最终高亮和引用预览必须如实呈现，并以用户明确点击的范围为准；是否允许这种交互需要与项目的精确选区需求对齐。

## 推荐的引用 Module

以下是待实施设计，不是新增正式 DTO 或已验证 Interface。持久化仍归项目，第三方对象只留在引擎 Adapter 中。外部调用只需要“从当前消息选区建立引用”和“从冻结引用生成展示／模型载荷”，不暴露 KaTeX AST、MathLive Atom、DOM 节点或 Windows 路径。

### 1. 不可变来源与引用内容分离

每条引用至少区分三层：

| 层次 | 保存的事实 | 不承担的职责 |
| --- | --- | --- |
| 来源 | 当前聊天／消息身份、可核对的消息修订或内容 hash、公式块在原始消息中的位置 | 不等于把整条来源再次加入引用载荷 |
| 选区 | 有序的文字范围／公式节点片段，包含必要分支关系；明确版本与位置单位 | 不要求一定是一个连续原文区间 |
| 表示 | 对已选内容的文字、公式或片段卡片；可按结构生成模型载荷 | 不成为新的来源真相，不把额外数学内容补入 |

原始 Markdown／LaTeX 继续不可变保存，用于核对来源。新表示可规范化空白或添加展示所需的分隔符，但不能改变选中符号、顺序或结构关系。必须明确区分“原文切片”和“由所选结构生成的表示”。不能通过 Compute Engine 化简、重排或数学等价校验来认定引用正确。

普通文字继续采用明确的原始 UTF-16 范围；公式采用有版本的结构路径／片段选择。MathLive offset 和临时 `data-atom-id` 只能在当前渲染中使用，不直接升格为长期业务身份。消息追加、宏策略、引擎更新或规范化变化时，旧引用绑定旧修订，不到新内容中猜一个相似位置。

W3C Web Annotation 将来源状态与选择器区分，并指出位置选择对内容变化敏感。本项目可借鉴其身份与选择分离原则，但其 TextPosition／TextQuote 使用 Unicode code point 及规范化文本，**不能把项目现有 UTF-16 源码下标直接改名为该标准选择器**。本项目不需要引入完整 JSON-LD 协议，也不需要自动模糊重定位旧引用。[W3C Web Annotation Data Model](https://www.w3.org/TR/annotation-model/#selectors)

### 2. 统一协调文字与公式选择

消息级选择 Module 统一管理一次手势的 anchor、focus、方向、所属消息修订和选择世代：

- 普通文字使用 DOM Range；公式内部优先使用 MathLive 的公开命中测试与位置能力。公式按展示结构处理，不按求值后的数学语义改写。
- 跨文字／公式、跨两个公式时，生成有序片段列表；不能只读 `window.getSelection().toString()`，也不能读取上一手势残留的 mathfield selection。
- 采用严格选区策略：不调用会把范围扩成整个父式的默认行为来“补成功”。公开选择原语是否足以实现，需在最小验证中确认；不足部分集中在固定 Adapter，禁止在各 UI 调用方增加符号特例。
- 临时高亮与待添加卡片必须表达同一组内容。滚动、重排、切聊天、流式更新或鼠标反向拖动不能改变已冻结选区；来源修订变化时显式处理过期状态，不能悄悄读取新版公式。
- 普通选中与复制不入草稿，不持久保存引用，也不派发模型；只有用户点击临时添加入口才冻结引用。现有快捷键、普通文本选择及只读属性需要分别回归。

浏览器 Selection 提供的是文档范围，而不是数学子式；Shadow DOM、内部编辑控制的选区还需要额外协调，规范也不会替项目生成数学选择结构。[W3C Selection API，2026-06 工作草案](https://www.w3.org/TR/2026/WD-selection-api-20260611/)

### 3. 允许片段，保留结构，避免错误数学含义

建议先支持下表的结构规则，再用嵌套组合扩展，不按具体公式字符串写分支：

| 实际所选 | 引用的表示 | 必须避免 |
| --- | --- | --- |
| 普通同层符号／等式的一部分 | 按原顺序组成一个公式片段 | 插入选区之外的项 |
| 分子中的 `a+b` | 独立子式 `a+b` | 把分母补入 |
| 根式内部的 `x+y` | 内部子式 `x+y` | 自动加上未选根号 |
| 只有下标 `i` | 明示为下标片段，可保留其展示位置特征 | 加上未选底数 |
| 矩阵首行的 `1` 与 `2` | 标为矩阵局部，保留两个单元格及其行列关系 | 串成数值 `12`，或补上第二行 |
| 上下两个分支的部分内容 | 多个带分支角色的片段；无法表达时明确提示 | 拼成一个看似完整但含义改变的公式 |
| 整条公式／整步推导 | 保留完整结构和原来源 | 因句点、不可见 strut 等 DOM 细节误拒绝 |

矩阵片段的行列身份和“下标片段”等角色用于说明已选内容的关系；不加载未选符号值作为上下文。既有对话历史继续按项目原有上下文规则处理，引用功能不另外扩大素材范围。

这需要表示层的树裁剪／片段序列化，不能把 `getValue(selection, 'latex')` 的结果直接写进 `markdown`。展示可以使用安全的结构化渲染；对缺失操作数采用明确片段标签或分开显示，不把展示占位误传为原文中存在的数学条件。

### 4. 后台重新生成并校验引用内容

这是引擎选择前必须解决的落地点，不能为了兼容 MathLive 而删除后台来源检查：

1. 后台先核来源消息属于当前聊天，读取明确修订／hash 和公式块；其他聊天、过期来源或篡改内容必须拒绝。
2. 基于可信来源，由相同版本的纯解析／投影 Implementation 得到可复核的结构索引，校验节点路径、片段关系、数量和深度限制。
3. 根据验证后的所选结构重新生成保存内容与模型载荷；不直接相信浏览器上传的自造 `latex`、任意 HTML 或整份节点清单。
4. 引擎临时 offset 先转换为项目拥有的版本化结构选择，再提交。若需要 Node，可由 Python 经现有进程管理方式调用固定的无 DOM 核心；必须先验证其纯函数能力，不为引用默认引入常驻 Chromium。

本次只验证了 MathLive 的公开 SSR 转换，没有验证一个可供后台复核的完整纯结构索引 Interface。**这一项是优先技术门槛，不是已经具备的能力。** 若公开 Interface 不足，比较两种有限成本：在固定 MathLive Adapter 中导出必要的纯解析投影，或用 MathJax 的结构树作为整个链路的统一投影。不能把两个不同解析器各自输出的树假设成天然相同。

因此推荐的来源定位是“原始消息／公式块 + 同版本可信结构路径”，不再要求每个片段都是原始字节的独立连续子串；同时保留原始字节供来源回看。只有确能取得原文切片的部分，才声明它是原文切片。

### 5. 兼容旧引用与草稿提交

- 旧 `DraftReference` 作为 v1 原样读取和校验，不重写旧引用或重新生成旧回答，不把历史 source_start/source_end 解释为结构 offset。
- 新表示采用显式版本或类型分支；实际字段从正式 DTO 生成 OpenAPI 与前端类型，本报告不维护第二份正式 schema。
- 沿用草稿 revision、当前聊天绑定、提交身份和清空对账。引用在加入草稿后冻结，发送时再次核来源，不能让旧回调覆盖新聊天草稿。
- 新版本对引用的持久化可优先复用现有 JSON 载荷与不可变提交条件，是否需要迁移以实际 schema 为准，不先设计新数据库平台。
- 来源失配、选区过期、结构暂不支持和展示暂不可用分别报告稳定状态；不能再全压成一个要求“缩小选区”的提示。

### 6. 明确的备用方式

结构无法准确表达时，保留既有软件内截图能力，由用户主动选择并确认“以选区图片引用”。不从选区外补取屏幕、整帧、相邻帧，也不默认让模型 OCR 重新识别已有公式。普通 DOM 选区的 bounding box 可能包住未选内容，不能直接把整个包围盒截图当作已经确认的原选区。

截图模式必须明确提示实际图片范围，并经用户确认后作为附件；不增加自动发送或模型降级。图片不支持当前用户选择的模型时按现有能力规则处理，不自动换模型。纯图像路线不是日常公式局部引用的替代验收。

## 按结构验证，避免继续按例子穷举

基础集合包括普通符号／命名算符、上下标、分式、根式／装饰、矩阵／cases／多行环境、文本与公式混排。每类组合两层以上嵌套，并覆盖重复符号、相同公式、多条引用、正反拖选、不同缩放、滚动与流式来源更新。

在固定 seed 的生成／性质测试中验证不变量：

- 输出内容只能来自实际所选片段；未选的叶节点不能进入载荷。
- 片段顺序、矩阵单元格和上下分支身份保留，不能通过串接产生不同的表达式。
- 同一修订与同一最终选区在相反拖选方向下得到一致引用；重新加载后的卡片及模型载荷与冻结内容一致。
- 空白、标准定界符和非 BMP 字符不改变来源定位；结构路径和 UTF-16 范围不混用。
- 取消选择、普通复制、来源变化和切聊天不创建引用；加入草稿不派发模型，失败不清空其他输入。
- 篡改来源／内容／结构版本在后台失败；不能靠修改客户端所报 hash 通过来源校验。

生成测试不能替代真实鼠标、Shadow DOM 和视觉检查。真实 Chromium 需独立断言高亮、卡片及所选符号，并用 fixture 检查实际提交内容；不以“没有抛异常”或“库成功输出字符串”作为通过标准。用户旧失败样例继续保留回归，但不作为唯一测试来源。
