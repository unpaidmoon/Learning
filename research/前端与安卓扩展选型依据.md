# 前端、视频截图与后续安卓扩展选型依据

研究日期：2026-10-18。本文只完成需求和官方文档、源码核对；未安装应用依赖、播放验收视频、抽取视频画面、转写音频或调用收费模型，也未上传视频。

架构更新：后续用户已明确 Windows 以 DeepSeek Harness＋插件为执行层主选，业务 schema 由本项目统一管理，安卓不运行完整 Harness。本文前端与媒体选择继续作为依据；涉及“本地 Python 后台负责模型请求”“不绑定另一套执行层”的旧讨论属于更新前方案，当前以新的整体技术方案及《Harness界面复用与开销验证计划.md》为准。UI 插件需要宿主适配和真实流式/取消验证，不能直接视为可迁移的 React 组件库。

本文中的「事实」来自所附官方来源；「建议」是结合本项目需求的设计判断；「待测」不是已经通过的能力。

## 1. 推荐结论

| 部分 | 首选 | 选择依据与边界 |
| --- | --- | --- |
| 前端 | React 19 稳定版＋TypeScript＋Vite | 完全定制的本地 SPA，无首版 SSR、SEO 或云端全栈部署需求；产出静态资源，由本地后台同源提供 |
| 基础界面 | shadcn/ui 按需引入源码＋Tailwind CSS | 统一课程、视频、聊天和编辑交互；仅取所需组件，不套用整套 AI 聊天产品 |
| 视频 | `@videojs/react` 10 的原生 Video 组件与可编辑控制皮肤 | 复用播放器控件和无障碍行为；MP4 仍由原生 HTML video 解码，不引入 HLS/DASH 引擎 |
| 主动截图 | 原生 Canvas API | 用户点击后才从当前 video 帧取得截图，以视频原始像素计算，而非截取缩小后的页面 |
| 图片编辑 | React Advanced Cropper，先通过 React 19 兼容性验证 | 同时支持自由选区、缩放、平移、保存裁剪状态和导出；React Image Crop 为较轻后备 |
| 消息显示 | 自定消息组件＋react-markdown＋remark-math＋rehype-katex/KaTeX | 公式、题目来源卡片、工具状态与输入附件由项目掌握，不绑定某个聊天 SDK 的消息协议 |
| 前端状态 | TanStack Query 管理后台数据；Zustand 管理界面和临时编辑状态 | 视频、截图、任务和聊天流避免共用一个频繁刷新的全局对象；持久化聊天不交给内存状态库 |
| 安卓后续 | 复用 Web 界面；预留 Capacitor 适配层 | 不将几十 GB 文件持久存储、后台同步和独立 API 调用预先承诺为纯 PWA 的必然能力 |

以上为首选组合，不是已经锁定和验证的依赖清单。版本通过最小闭环验证后写入锁文件；禁止直接跟随 `latest` 或 `next` 自动升级。

## 2. React、Vite 与整体界面

事实：React 官方提供 Vite 的 `react-ts` 建立方式，同时说明自行组织 SPA 要自己承担路由、数据获取等职责；当前官方 React 版本页列出的最新稳定系列为 19.3。Vite 可生成可由静态服务提供的生产资源，TypeScript 转译不等于完整类型检查，构建检查应另跑 `tsc --noEmit`。[React 官方 SPA 指引](https://react.dev/learn/build-a-react-app-from-scratch)、[React 版本](https://react.dev/versions)、[Vite 生产构建](https://vite.dev/guide/build)、[Vite TypeScript 说明](https://vite.dev/guide/features.html)

建议：选择 React＋Vite，而非为本地学习页面引入 Next.js 服务端渲染。后端继续独立负责资料、本地文件、任务与模型调用，开发时由 Vite 代理相应 URL，生产时由同一个本地服务提供页面和 `/api`。这使视频、截图和 API 同源，也便于后续将静态界面打入安卓壳。此处不是声称 React 比其他框架运行更快，而是组件生态和复用边界更贴合当前需求。

事实：shadcn/ui 允许将组件源码放进项目并直接修改；Tailwind 官方提供 Vite 插件集成方式。[shadcn/ui](https://ui.shadcn.com/docs)、[Tailwind Vite 安装](https://tailwindcss.com/docs/installation/using-vite)

建议：只引入按钮、菜单、对话框、分隔拖拽、输入框、提示和进度等基础能力。学习页面自行组合为课程导航、视频、聊天、附件编辑区，不复用他人产品的整体布局和工具流程。

事实：TanStack Query 负责请求、缓存和后台状态更新；Zustand 支持按状态选择器订阅以及 React 之外的 store。[TanStack Query](https://tanstack.com/query/latest/docs/framework/react/overview)、[Zustand 官方仓库](https://github.com/pmndrs/zustand)

建议：两者分工要明确。课程、会话、任务快照属于后台数据；当前选区、缩放、输入框状态属于界面状态。播放进度和模型流只更新相关组件，不逐 token 重建整个播放器与长聊天列表。不要同时在 Query、Zustand 和本地数据库里维护三份可写的聊天真相源。

两项依赖在本项目有各自价值：Query 处理课程、会话分页、任务快照的请求去重、刷新和错误恢复；Zustand 处理播放器、附件编辑器和输入区之间的小量共享状态。不要为模型每个 token 建 Query，也不要将 video DOM、Canvas、Blob 或完整视频放入可序列化的全局状态。最小验证页面可先用 React 本地状态，完整首版再按上述职责接入，避免测试页面为框架组织耗时。

## 3. 视频播放器的选择

### 3.1 Vidstack 已不宜作为新项目主选

事实：核对时 Vidstack 官方仓库明确标记弃用，仅为 1.x 维护优先安全修复至 2028 年 1 月；相关维护团队转向 Video.js 10。官方迁移文档也强调新 API 不是简单改名，迁移存在重写成本。[Vidstack 官方仓库](https://github.com/vidstack/player)、[Video.js 官方迁移说明](https://videojs.org/docs/framework/react/guides/migrate-from-vidstack)

因此，本项目不因为旧文档较丰富就采用 Vidstack。该发现也说明选型应核对项目当前维护状态，不能只看功能清单或历史印象。

### 3.2 原生 video 与 Video.js 10 的取舍

| 方案 | 价值 | 项目成本 |
| --- | --- | --- |
| 原生 `<video controls>` | 最少依赖，直接访问 video 元素；足够做播放和截图基线 | 默认控件难以深度统一；自建倍速、热键、字幕与无障碍控制会形成额外维护 |
| `@videojs/react` 10＋原生 Video | 播放状态与 UI 组件可组合，皮肤源码可进入项目修改 | 增加一项播放器依赖，新版 API 与字幕边界需要实测 |

事实：Video.js 10 的 `Video` 保留原生 video 属性、事件与子元素，不替代浏览器的视频解码 API；官方 React 安装页当前示例固定为 `@videojs/react@10.1.0`，并提供将皮肤源码加入项目的方式。[Video 组件](https://videojs.org/docs/framework/react/reference/components/video)、[React 安装与皮肤](https://videojs.org/docs/guides/installation/react)

建议：以 `@videojs/react` 10 的原生 Video＋可编辑皮肤为产品首选；可先用原生 video 控件做兼容基线。定义很薄的播放器接口，暴露 `play/pause/seek/currentTime/videoWidth/videoHeight` 与用户主动的 `capture`，避免聊天模块依赖播放器内部 store。若新版播放器在首轮样本上引入额外问题，退回原生 video 和有限控制按钮，不替换整个应用。

### 3.3 本地长视频的供应方式

现有样本来自需求记录：MP4、H.264＋AAC、960×720、约 510 MB、3 小时 25 分钟。此研究没有重复探测或播放它。

事实：HTTP Range 支持客户端请求文件片段，成功使用 `206 Partial Content`、`Content-Range`，越界请求使用 `416`；适用于随机访问媒体。浏览器 `canPlayType()` 只能报告 `maybe/probably` 等兼容倾向，不能代替实际播放。[HTTP Range](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Range_requests)、[canPlayType](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/canPlayType)

建议：本地后台以资料 ID 映射用户已导入的文件，提供同源 `/media/{assetId}` Range 接口，复用成熟文件响应实现。支持 HEAD、正确 MIME、长度和文件版本验证。浏览器使用此 URL 直接播放；不先 `fetch` 完整视频再转成 ArrayBuffer/base64，也不复制源视频到前端目录。

推断：该样本编码适合作为 Windows 现代 Edge/Chrome 的直接播放首轮候选，无理由预先整课转码或改成 HLS。是否可直接播放、跳至后半段的速度，以及容器头部位置带来的差异，都必须用真实文件测试。若确有容器或编码问题，再按文件提供兼容处理，不能将全量转码设为默认导入步骤。[MDN 视频编码说明](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Video_codecs)

首版播放环境建议只验收现代 Windows Edge/Chrome；其他编码、浏览器和安卓 WebView 在对应阶段明确。

## 4. 截图、裁剪与模型输入

事实：`drawImage` 可以接受 HTMLVideoElement，并支持以源图坐标裁剪；计算应使用 `videoWidth/videoHeight` 而非 CSS 显示宽高。Canvas 可以用 `toBlob()` 导出；跨源资源未正确启用 CORS 时可能污染画布并阻止导出。[drawImage](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/drawImage)、[toBlob](https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/toBlob)、[Canvas 跨源规则](https://developer.mozilla.org/en-US/docs/Web/HTML/How_to/CORS_enabled_image)

建议的用户触发链路：

1. 用户点击截图或截图快捷键，固定当前显示帧并记录来源资料 ID、播放时间。
2. 使用原始视频像素取得这一次主动截图，进入编辑器；不启动后台逐帧抽图。
3. 用户自由框选、缩放、平移并确认；原始截图与裁剪坐标本地保留，支持重新编辑。
4. 生成用户确认选区对应的 Blob，显示在提问附件中；多图可删除、替换、重新裁剪。
5. 发送时只提交已确认的选区图和用户文字；原图、相邻帧不因保存在本机就自动交给模型。

缩放用于看清和操作选区，不代表能恢复原始视频没有的细节。原始 960×720 内容不应因页面显示缩小而再降采样；默认先用 PNG 保留小字、上下标和线条，实际提交格式、图片尺寸与模型计费效果再做测试。压缩字节数不一定等比例减少图像 token。

事实：`requestVideoFrameCallback` 可用于与视频帧呈现同步。[官方 API 说明](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback)

建议：仅在用户截图或 seek 后需要确认画面就绪时使用对应机制，暂停帧采用已呈现帧与 readyState 检查。不能为“方便截图”持续采集视频；截图之后是否继续播放属于交互细节，不应阻塞附件进入聊天。

### 4.1 图片编辑组件

事实：React Advanced Cropper 提供 `zoomImage`、`moveImage`、`getCoordinates`、`getCanvas` 等方法，可自定义选区和界面；其源码包声明 React `>=16.8`，但仓库开发测试依赖仍为 React 17。[操作示例](https://advanced-cropper.github.io/react-advanced-cropper/docs/guides/advanced-recipes/)、[Cropper API](https://advanced-cropper.github.io/react-advanced-cropper/docs/components/Cropper/)、[包源码](https://raw.githubusercontent.com/advanced-cropper/react-advanced-cropper/master/package.json)

事实：React Image Crop 官方声明支持自由选区、触摸、键盘和较小体积，其当前源码已使用 React 19 开发依赖；它主要处理选区，不直接提供完整缩放平移编辑器。[官方仓库](https://github.com/dominictobias/react-image-crop)、[包源码](https://raw.githubusercontent.com/dominictobias/react-image-crop/master/package.json)

建议：首选 React Advanced Cropper 完成最短编辑链路，但把 React 19 下的选区恢复、鼠标滚轮、平移、窗口缩放、导出坐标一致性列为接入门槛。若出现兼容或维护问题，再采用 React Image Crop＋有限缩放视图；避免初版就叠加多套手势库、自行重复实现全部几何计算。编辑模块只输出源图坐标和附件结果，不将组件专有状态写成跨端业务格式。

## 5. 聊天、数学公式与流式交互

事实：react-markdown 提供 React 组件替换和插件机制，官方给出 remark-math＋rehype-katex 的公式渲染示例，默认不需要 `dangerouslySetInnerHTML`。KaTeX 官方描述了 `trust` 等安全配置。[react-markdown](https://github.com/remarkjs/react-markdown)、[公式插件](https://github.com/remarkjs/remark-math)、[KaTeX 配置边界](https://katex.org/docs/security)

建议：使用成熟 Markdown 和公式组件，自行组合消息外壳、输入区与来源卡片。不引入带另一套 agent runtime、模型路由或会话存储的聊天框架。消息持久格式与 UI 分开，明确用户文本、图片附件、回答内容、引用和工具状态等字段。

前端采用一条可取消的后端流，展示回答文本与“读取字幕/检索资料”等明确事件；流式 Markdown 按小批次更新，未闭合数学片段先显示原文，闭合后渲染，避免每个 token 重排全部公式。具体节流和长消息优化由真实播放＋聊天并行场景验证，不预设“某框架天然更省 token”。

可作为起点的实现策略：流增量先写入专属缓冲区，每 40～80 毫秒批量刷新一次当前回答；已完成消息和播放器使用独立订阅及稳定 props，进度、输入和回答不共享整个页面的 render 依赖。该间隔是可调整的工程初值，不是性能承诺。保留消息渲染边界，只在长历史实际出现卡顿后引入列表虚拟化；避免虚拟化卸载公式、改变滚动高度又造成体验问题。

省 token 的前端贡献主要是明确发送范围、裁剪选区、来源元数据和附件引用；上下文裁剪、按需字幕、检索以及模型调用次数仍由应用编排层控制。普通截图提问不额外先做一次 OCR 模型调用，也不把全部字幕作为隐形默认附件。

## 6. 后续安卓：可复用代码的边界

### 6.1 PWA 可以做什么，不能预先保证什么

事实：浏览器 IndexedDB、Cache、OPFS 都受存储配额管理；普通存储在空间压力下可能被清理。`navigator.storage.persist()` 是申请而非保证，Chromium 可以静默拒绝。[浏览器存储说明](https://web.dev/articles/storage-for-the-web)、[配额与驱逐](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)、[持久化申请](https://web.dev/articles/persistent-storage)

建议：PWA 可用 IndexedDB 保存结构化记录、OPFS 保存文件、Service Worker 缓存应用壳。但不能据此承诺几十 GB 课程永不丢失，必须检查额度和持久化结果，并有导出恢复机制。首版 Windows 不提前建立一套完整移动数据库和同步引擎；先把界面业务与平台文件、存储、网络分开。

事实：Service Worker 需要安全上下文，localhost 可例外；安卓访问电脑的普通 HTTP IP 地址不能视为安卓本机 localhost。后台任务也可能被浏览器终止，Background Sync 不适合无限持续的任务。[Chrome 安全上下文说明](https://developer.chrome.com/docs/workbox/improving-development-experience)、[PWA 离线与后台](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Offline_and_background_operation)

建议：后续通过 HTTPS 提供移动端应用。Tailscale 可以提供连接与 HTTPS，但不改变各端数据库、同步协议、浏览器存储配额和后台生命周期。Windows 关闭网页后继续转写由独立后台承担；安卓恢复同步应在打开、回到前台、网络恢复时重试，不能只依赖后台事件。

### 6.2 Capacitor 的候选价值

事实：Capacitor 可提供原生 HTTP、文件与文件传输接口；官方提示大量数据通过 JS/native HTTP 桥可能有问题，并将 Filesystem 的 `downloadFile` 弃用，推荐 File Transfer 配合 Filesystem。[Capacitor HTTP](https://capacitorjs.com/docs/apis/http)、[Filesystem](https://capacitorjs.com/docs/apis/filesystem)、[File Transfer](https://capacitorjs.com/docs/apis/file-transfer)

建议：Android 若需稳定的大文件离线下载、文件 URI、本端凭据和独立网络能力，优先以 Capacitor 包装相同 Web 前端并增加平台适配；视频保持在原生文件目录，传 URI，不传完整 base64。是否需要这一层，待安卓阶段实机验证后决定，不在首版增加原生打包工作。

必须保持的事实边界：浏览器跨域请求受 CORS 约束；不能从 API 兼容 OpenAI 推出浏览器可直接调用。密钥不能写进 Vite 构建产物；Windows 由本地后台持有，安卓独立调用需按设备管理凭据，原生端可使用 Keystore 适配。[CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)、[Capacitor 安全建议](https://capacitorjs.com/docs/guides/security)

待测：DeepSeek 官方端点的实际 CORS、图片与 SSE；`CapacitorHttp.request()` 返回完整响应，不据此声称已经支持逐 token SSE。若采用原生请求，需要另验证增量流、取消和中断恢复。Capacitor 壳本身也不保证 Android 长期后台执行。

建议只为这些可替换位置定义接口：本端资料定位与读取、数据仓库、模型请求通道、同步通道。同步实体使用稳定 ID 和文件指纹，不把 Windows 绝对路径当成跨端文件身份。

## 7. 首轮验证与采用门槛

以下验证尚未执行，不需要提前扩展成完整应用：

1. Range：样本初次打开、跳至接近结尾、多次随机 seek，不在网页内存载入整段视频；确认 206/416/HEAD 行为。

4. 连续聊天：流式文字与数学公式、停止生成、播放不被重建；较长历史不拖慢输入。
