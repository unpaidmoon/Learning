# 本地后台与语音转写选型依据

> 当前适用性补充（2026-10-20）：保留历史选型与证据；正文字幕AI纠错/校准相关队列与调用已取消，不迁入当前实现。当前字幕/手改/覆盖/暂停/资源验证见[V6](/D:/Codex/Learning/docs/验证/V6-字幕与前台并行执行方案.md)，运行/睡眠/统一启动见[V7](/D:/Codex/Learning/docs/验证/V7-资产迁移与Windows运行执行方案.md)。短段推理不证明整课/并行或交付环境通过。

> 历史研究状态：本文记录的是首次技术选型依据。用户随后明确选择 Windows 以 DeepSeek Harness 与适用插件作为执行层主选；新的执行接入评估见《Harness定制前端与Windows执行接入评估.md》。正文保留当时的比较过程，其中「Node 仅用于前端构建」「不依赖 Harness」等互斥推论不再代表最新架构。Python 本地业务服务、独立 ASR worker、持久 GPU 任务调度和相关环境检查仍可作为当前设计依据。

核对日期：2026-10-18。适用范围：Windows 单人首版、本地后台＋浏览器、自主截图和文字优先解题。本文区分官方能力、本机只读检查和设计建议；没有执行视频转写或模型问答。

## 1. 推荐决定

推荐 **Python 3.12 系列＋FastAPI／Uvicorn 本地服务＋独立 Python 转写进程＋SQLite 持久任务表＋FFmpeg／ffprobe＋watchdog**。语音引擎首选 **faster-whisper／CTranslate2**，使用其已有 Silero VAD 集成。模型先比较多语言 `turbo` 与 `large-v3`，以实际数学网课的准确性、前台影响和处理速度选定，不预先承诺 8GB 显存下的具体耗时或峰值占用。

初版不引入 Redis、Celery、Docker 或 WSL 作为运行前提。任务调度保留独立接口，以后出现多机处理需求再替换。Windows 是 Celery 官方明确不支持的平台，本项目没有理由为了单机队列增加这一依赖。[Celery FAQ](https://docs.celeryq.dev/en/stable/faq.html#does-celery-support-windows)

上述是技术方案建议，不是已经完成的应用或通过验收的组合；具体补丁版本由隔离环境解析、功能检查和依赖加载结果共同锁定。

## 2. 后台技术栈比较

| 方案 | 对本项目的价值 | 额外代价 | 建议 |
| --- | --- | --- | --- |
| Python FastAPI 主后台＋独立 Python worker | 本地转写、资料处理和业务 API 共用 Python 生态；接口使用 OpenAPI 向前端提供类型契约；只需要一套后台主语言 | 前端与后台仍需维护 HTTP／事件契约；重型调用必须隔离，不能堵住 API 进程 | 首版采用 |
| TypeScript 主后台＋Python worker | 前端与业务服务可共用 TypeScript 模型；若核心 Agent 框架只能在 Node 中使用，接入更直接 | 同时维护两个后台运行环境、进程生命周期、错误与事件协议；ASR 仍需 Python | 作为有明确复用收益时的替代方案 |

这是基于本项目边界和依赖数量的工程判断，并非宣称 Python 请求吞吐高于 Node。当前前台主要成本在模型网络调用、图片处理和视频解码；选择后台语言本身不会减少模型 token。

首版主服务负责课程目录、资料映射、聊天请求、流式响应、任务操作和状态事件；转写 worker 只通过稳定的任务输入、进度与产物协议参与。不把领域逻辑放进 HTTP 路由或模型 SDK 中。后续安卓端可以复用接口和数据规范，不依赖本机 Python 才能保存记录、调用模型。

## 3. 视频服务和 Windows 生命周期

### 3.1 按需读取视频

- H.264／AAC 的用户样例优先直接供浏览器播放，不默认转码或复制视频。
- 通过已登记的 `asset_id` 映射原路径，并使用支持 HTTP Range 的文件响应；需要验证 `HEAD`、`206 Partial Content`、`Content-Range`、拖动跳转和请求取消。不要把 510MB 文件完整读入 Python 字节串，也不要只手工加一个 `Accept-Ranges` 头就认为支持跳播。Starlette `FileResponse` 已包含 Range 处理，但采用的具体版本仍需实际验证。[FileResponse 源码](https://github.com/Kludex/starlette/blob/main/starlette/responses.py)
- 首版允许的自动媒体处理只有音频读取等已授权能力；不会自动抽取视频画面参与问答。截图由用户在浏览器播放器中主动触发。

FastAPI 的 Starlette 依赖要由隔离环境解析，不能依赖全局环境碰巧安装的版本；验证后把完整解析结果写入锁文件。官方建议由 FastAPI 选择合适的 Starlette，再固定已验证的 FastAPI 版本。[FastAPI 版本说明](https://fastapi.tiangolo.com/deployment/versions/)

### 3.2 网页关闭后继续运行

- 启动器启动一个后台实例，探测健康状态后打开浏览器。网页关闭不触发后台退出。
- 本地服务、任务调度和 worker 由后台进程管理。界面显示运行状态、暂停和明确退出入口；开发模式的热重载进程不作为实际交付启动方式。
- Windows 后台子进程隐藏控制台窗口，使用参数列表启动 FFmpeg，不用 shell 拼接文件路径。独立进程可以使用 Python `subprocess`；Windows 的进程启动不能假定 Unix `fork` 行为。[Python subprocess](https://docs.python.org/3.12/library/subprocess.html)、[multiprocessing](https://docs.python.org/3.12/library/multiprocessing.html)
- 重启后恢复任务，含义是用户再次启动后台时根据持久状态续做；不默认设置开机自动启动。

## 4. 持久任务与前台优先

### 4.1 不使用请求内后台任务承担整课转写

FastAPI `BackgroundTasks` 是响应后执行的便利机制，官方对重型计算也建议考虑独立执行设施；它本身不能提供本项目所需的持久队列、重启恢复、优先级和片段检查点。[FastAPI Background Tasks](https://fastapi.tiangolo.com/tutorial/background-tasks/)

首版使用独立 worker 进程，API 服务不加载 ASR 模型。一次只运行一个 GPU 转写任务，避免重复模型驻留挤占显存；字幕纠错是另外的低并发云端 I/O 队列，当前解题请求优先占用模型请求容量。

### 4.2 SQLite 任务表

任务至少保存：`job_id`、`asset_id`、源文件修订号、任务类型、时间范围、模型及参数版本、优先级、状态、尝试次数、租约／心跳、下次重试时间、产物引用和检查点。

- 任务状态包含排队、执行、暂停、完成、失败和取消请求，不能仅以一个内存列表表示进度。
- 以「资产修订＋处理器版本＋时间范围＋参数摘要」生成去重键。发生崩溃后，可以重复执行未提交片段，但不能重复提交同一产物。
- 用短事务原子领取任务，计算和网络调用在事务之外执行；配置有限重试和超时。SQLite 同时只能有一个写事务，不能让 ASR 持锁等计算。[SQLite 事务](https://sqlite.org/lang_transaction.html)
- 主服务和 worker 可以各自使用连接并提交短事务；也可以统一经任务仓储调用。接口先稳定，不建设通用分布式工作流平台。
- WAL 可改善同机读写并发，但不应把 SQLite 文件作为多端同步文件放到网络盘；以后各端通过业务协议同步记录。[SQLite WAL](https://sqlite.org/wal.html)

**必须核对 SQLite 实际运行库版本。** 本机 Python 的 SQLite 是 3.45.3。官方说明 WAL-reset 问题已在 3.51.3 及以后修复，并回补到 3.44.6、3.50.7；本项目若使用多连接 WAL，应选择带修复的实际运行库，不能仅凭 Python 小版本判断。这个要求不会改变采用 SQLite 的决定。[SQLite WAL-reset 说明](https://sqlite.org/wal.html#the_wal_reset_bug)

### 4.3 调度顺序与暂停语义

1. 前台聊天、视频 Range 读取、截图上传和本地保存。
2. 当前问题明确依赖的字幕时间范围及其纠错。
3. 当前观看位置的相关片段。
4. 整课剩余转写、批量纠错、文档索引等后台任务。

优先级调度发生在**下一个片段开始之前**。不声称可以即时抢占已经执行中的 GPU 推理；暂停时在当前小片段完成并保存后停下。强制退出可能重做当前未提交片段，已提交片段不重做。

建议以 30～60 秒音频片段和少量相邻重叠作为测试起点，结合停顿调整边界；最终片长由单片延迟、术语准确率和调度等待共同决定。过长片段影响插队和暂停，过短片段损失上下文并增加边界处理。字幕时间使用原视频绝对时间，重叠内容要去重，不能因为拼接音频改变引用位置。

## 5. 音频和转写流水线

### 5.1 FFmpeg 与增量解码

`ffprobe` 用于读取容器、流、时长、编码和字幕轨道信息，结果结构化保存。[ffprobe 官方文档](https://ffmpeg.org/ffprobe.html)

`FFmpeg` 用于按时间范围读取音频、转换为 ASR 所需的单声道采样格式，并产生有限长度的临时片段；不把整个 3 小时 25 分钟视频一次解码成 PCM 后长期驻留内存。优先片段可以直接定位提取，其他片段在后台依次处理。缓存音频设置容量与清理规则，已完成字幕及其时间戳长期保存。[FFmpeg 时间范围和音频参数](https://ffmpeg.org/ffmpeg.html)

faster-whisper 自带的 PyAV 解码意味着其普通使用不强制依赖系统 FFmpeg，但本项目仍保留 FFmpeg 作为媒体处理工具。当前 `decode_audio` 实现会收集所给输入的音频数据，因此应把有限范围片段交给它，避免把整课当成单个工作项。[音频解码源码](https://github.com/SYSTRAN/faster-whisper/blob/master/faster_whisper/audio.py)

### 5.2 引擎、模型与起始参数

faster-whisper 使用 CTranslate2，提供 GPU FP16、`int8_float16`、时间戳和 Silero VAD 集成；官方仓库的显存与速度表是在特定 GPU、音频和参数上测得，不能作为本机数学网课承诺。[faster-whisper](https://github.com/SYSTRAN/faster-whisper)

建议首测：多语言 `turbo`、`device=cuda`、`compute_type=int8_float16`、显式 `language=zh`、`task=transcribe`、单 worker、非大批量模式、保留片段时间戳。`large-v3` 作为术语识别对照；若影响前台或出现资源不足，再评估较小模型。不要使用英文专用 `.en` 模型。Whisper 官方也强调速度和效果依赖语言与硬件，官方原始实现的显存表不能直接套用于 CTranslate2 量化实现。[Whisper 模型说明](https://github.com/openai/whisper#available-models-and-languages)

开启 VAD 过滤静音，利用 faster-whisper 现有集成，不重复引入一套独立 PyTorch VAD 服务。数学推导中的长停顿、短语音和字母发音要单独测试，不能激进切除。Silero 提供 ONNX／PyTorch 使用方式，但这里优先使用已有 ONNX 集成。[Silero VAD](https://github.com/snakers4/silero-vad)

数学术语以短小的课程词表通过 `initial_prompt`／`hotwords` 提示，例如「拉格朗日中值定理、柯西、泰勒、齐次方程、洛必达」。这些是识别提示，不能保证公式和条件正确；不塞入整份讲义。`beam_size` 先保留基线，再比较 1 与 5 对术语、重复文字和速度的影响。当前引擎接口支持这些参数，但候选锁定版本仍需核查；prefix 等参数会改变 hotwords 的行为。[转写参数源码](https://github.com/SYSTRAN/faster-whisper/blob/master/faster_whisper/transcribe.py)

`batch_size` 不默认取 README 中的高吞吐示例值。先单任务、小批量，确认前台流畅后才提高吞吐。恢复、插队、去重和前台优先是本项目的调度逻辑，不是 ASR 库自动提供的能力。

### 5.3 字幕纠错和索引

- ASR 初稿带稳定片段 ID、原始文本、绝对时间和源文件版本，先可用于显示和检索。
- 纠错只发送当前文本、必要相邻文本和课程术语；不发送整节视频、不自动补取画面。只有用户已提交的图片可以作为补充证据。
- 纠错按短段合并请求，避免逐句网络往返；合并长度和 token 上限由实测确定。当前问题需要的片段可以优先纠错，普通整课优化保持后台低优先级。
- 返回结构化的片段 ID 和修正文，不让模型重新分配时间轴。提交时检查输入修订，过时结果不能覆盖手动修改或更新后的资料。
- 只有有效修正版参与检索；原始转写保留作回查。失败或未处理覆盖率必须能区分「尚未处理」与「确实未找到」。

## 6. 课程目录自动跟踪

采用 watchdog 监听已导入的课程目录；其 Windows 后端使用 ReadDirectoryChangesW。[watchdog 官方仓库](https://github.com/gorakhargosh/watchdog#supported-platforms)

事件先防抖、合并并等待文件大小／修改时间稳定，再做元数据探测和任务排队。后台启动时以及适当的空闲时段做轻量目录对账，避免把文件通知当成不会丢失的任务日志。

原文件路径与稳定资产 ID 分离。常规变化检测先用尺寸、修改时间等元数据；需要可靠验证移动或同名替换时再校验内容指纹，避免每次启动都重读几十 GB 文件。文件删除／移动不直接清除聊天和题目来源；处理任务保存源修订，变化后只失效受影响派生结果。

## 8. Windows 原生文件／课程目录选择器

### 8.1 原地引用不能依赖浏览器上传控件

本项目需要后台知道视频与课程文件夹的真实位置，才能直接提供 Range 视频和监听目录；浏览器文件输入不提供可以用于后台定位的真实绝对路径。因此「导入视频／导入课程」应调用本地原生选择器，返回路径后登记引用，不能先把视频经浏览器上传并复制一遍。

本机只读检查：没有 tkinter；已安装 pywin32 312，可导入 `pythoncom`、`win32gui` 和 `win32com.shell.shell`。后者有 `SHBrowseForFolder`／`SHGetPathFromIDList`，`win32gui` 有 `GetOpenFileNameW`；但没有 `IFileDialog`、`CLSID_FileOpenDialog` 导出。不能假设已安装的 pywin32 直接封装现代 IFileOpenDialog。另有 .NET Desktop 运行库，但 Codex 自带 PowerShell／WinForms 路径不应作为应用的永久运行依赖。本次没有创建或显示任何选择窗口。

### 8.2 最小实现推荐

推荐一个职责很小的 **Windows 原生选择器 helper**，以 Microsoft Common Item Dialog 的现有接口和官方样例为基础封装，不增加完整 GUI 框架。使用 Windows SDK 编译的小型 helper，只承担文件／目录选择和路径结果返回；业务仍在 Python 中。Microsoft 推荐现代 `IFileDialog`，目录选择可以复用 `IFileOpenDialog`＋`FOS_PICKFOLDERS`；结果通过 `IShellItem.GetDisplayName(SIGDN_FILESYSPATH)` 获取。[Microsoft Common Item Dialog](https://learn.microsoft.com/en-us/windows/win32/shell/common-file-dialog)、[Microsoft 官方示例源码](https://github.com/microsoft/Windows-classic-samples/blob/main/Samples/Win7Samples/winui/shell/appplatform/commonfiledialog/CommonFileDialogApp.cpp)

最小数据流：

1. 用户点击网页中的「添加视频」或「添加课程目录」。
2. 本地服务异步启动一次 helper；helper UI 线程初始化 STA COM，打开原生选择器。一个时刻只允许一个待选窗口，不阻塞 API 事件循环。
3. 按模式设置文件过滤或目录选取，并限定文件系统对象；接受或取消后，通过约定的 JSON／退出状态将绝对路径或取消状态返回本地服务。
4. 后台核验路径、登记 `asset_id`／课程根目录、读取必要元数据；后续视频请求和文件监听使用此登记关系。视频不复制、不上传，取消也不建立资料记录。

helper 应作为可复现构建产物随 Windows 本地应用交付，不能要求用户安装 C++ 开发工具。尽量采用无需额外 GUI 运行时的构建方式；具体二进制构建与依赖在开发阶段检查。常规后台没有可见控制台，只有用户主动触发的选择器可见。

若最初验证阶段暂未构建 helper，可在相同接口下用独立 Python STA 进程调用现有 pywin32 的 `SHBrowseForFolder`／`GetOpenFileNameW` 作为临时适配器；这属于旧式选择器，不把它描述为现代 Common Item Dialog，也不为此引入 tkinter。最终应检查原生窗口是否位于浏览器前方、中文／长路径、上次目录记忆、取消与重复点击，以及后台是否仍能继续提供服务。
