# 立项调研：数据、资料检索与多端演进

核查日期：2026-10-19（Asia/Shanghai）。

范围：沿用 **Windows Harness 执行层＋自有业务数据＋Python 处理模块**；后续安卓独立学习并按条件同步。首版仍以 Windows 视频截图、文字问答为主，禁止 AI 自动补取视频画面。本文不新增掌握度评估、个人投入产出分析或首版完整跨端开发要求。

证据分为官方文档/源码、局部实测、项目设计与待验收四类。Harness 既有接口依据固定提交 `687f282e8625c6b8d11ff58211a90524be2e4317`；本报告没有安装依赖、下载模型、调用付费 API、处理用户原素材或抽帧。今日仅重复执行内存 FTS 边界样例。

## 1. 可行性结论与实际缺口

**当前数据路线可用于立项，前提是先证明资料身份、附件持久化、执行接续与恢复边界。** 没有发现需要推翻 Harness 主线或为几十 GB 原始资料立即部署分布式数据库的理由；也没有依据认为现成组件已经完成完整学习知识库或安卓同步。

| 实际缺口 | 可能出现的错误 | 必须形成的交付证据 |
| --- | --- | --- |
| 原地引用的文件改名、覆盖或删除 | 旧引用跳到新题，误称旧视频仍可回看 | 稳定资料 ID、内容版本、位置映射与缺失状态 |
| 业务 DB、图片文件与 Harness 日志分开持久化 | 聊天已保存但题图丢失；恢复后重复生成 | 附件发布顺序、执行映射、终态对账及故障测试 |
| 中文 OCR/公式与题目完整性 | OCR“成功”却漏了第二问、图形或关键不等号 | 原页区域、题目模型、版本化解析与代表样例 |
| 增量全文/语义索引 | 初稿与修正版重复命中，旧向量搭配新原文 | 版本化索引发布、覆盖状态与失效重建 |
| 派生产物持续增长 | 截图、执行附件、日志、临时音频比原文件增长更快 | 分层体积统计、受保护资产与可回收缓存区分 |
| 备份不包含所有必需对象 | 数据库能恢复，原图/原件/执行状态却不可用 | 备份清单、导出版本、完整性校验和恢复演练 |
| 安卓“大文件离线”被理解为普通浏览器缓存 | 电脑关机后应用不能启动，或离线视频被清理 | 安卓阶段真实设备冷启动、持久化、容量与中断测试 |
| 同步与执行混为一个订阅 | 已完成安卓问题在电脑重新收费执行 | 独立的 SyncIngest、Submission 与 ExecutionBinding |

## 3. 最小业务实体与接口

### 3.1 实体职责

这些是应用契约建议，不是 Harness 的内部 schema，也不要求每一行立即成为独立数据库表。

| 实体组 | 最小身份与版本 | 关键约束 |
| --- | --- | --- |
| Course / Asset / AssetLocation | course/asset ID、source revision、设备位置、当前可用性 | 业务身份不使用 Windows 路径或文件名 |
| Blob / Attachment / EditRelation | 内容 hash、大小、媒体类型、原图尺寸、裁剪关系、用途 | 区分本地编辑原帧与用户提交图，模型只能读取后者 |
| Chat / Message / MessageRevision | chat/message/revision ID、角色、父关系、设备来源 | 完整消息保留；新增消息不由 LWW 覆盖 |
| Submission / Generation | 请求所有者、执行代次、状态、真实模型与 usage | completed 不因同步变成 pending；未知不是零费用/未执行 |
| ContextSnapshot / ExecutionBinding | 选定 revisions/frontier、snapshot hash、Harness 会话、epoch、事件水位 | 业务聊天与原生执行记录分开；可重建绑定，不强制用户另开聊天 |
| Task / SubtitleSegment | 来源修订、参数版本、时间范围、base revision、结果引用 | worker 旧结果不能覆盖新来源或用户编辑 |
| DocumentUnit / Locator / IndexBuild | 文档产物版本、题号/页序/区域、索引 generation、coverage | 题目可含多页多区域，当前索引仅指有效版本 |
| PlaybackSession / StudyRecord | 媒体版本、播放会话、位置、行为 ID、汇总版本 | 播放进度不是最大观看时间；行为不默认向量化 |
| ChangeEnvelope / ReplicaCursor / TransferManifest | mutation ID、实体修订、设备、同步游标、文件版本/字节进度 | 后续实现网络同步，数据模型现在保留可映射边界即可 |

时间和坐标明确单位：视频用整数毫秒及原媒体版本；页面使用显式页序字段和基准坐标、尺寸、旋转/CropBox 信息。PDF 页序、文件 page label、扫描图中的印刷页码分别保存，不用一个 `page=35` 混淆三者。

## 4. 原地引用：必须接受的版本边界

### 4.1 移动与覆盖是不同操作

- 文件仅改名/移动、内容相同：更新位置，保留 asset ID 和 source revision。
- 同路径内容替换：创建新的 source revision，新的解析/字幕绑定新版本；旧回答仍绑定旧版本。
- 删除/拔盘/权限不可读：保留资料目录、聊天和来源事实，标记当前不可用；重新定位后核验内容再恢复。
- 目录监听事件丢失：启动/恢复/监听异常后重新对账。Windows 官方明确通知缓冲区溢出时可能丢弃记录，需要枚举目录恢复。[ReadDirectoryChangesW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-readdirectorychangesw)

大小、mtime、文件名是低成本变化信号，不是内容身份。初次可以先登记并播放，再后台流式计算 hash；未确认 fingerprint 就保留 provisional 状态，不能将同大小文件认作已确认同一版本。后台解析结束发布前要核对来源修订，避免用一半旧、一半新的输入提交索引。

### 4.2 不能保证被覆盖原件的旧页永久回看

**既不复制原件、又保证原文件被删除/覆盖后仍能打开旧版完整视频，两者不能同时成立。** 默认原地引用继续保留，但应保证已经提交的题图、文字、必要引用快照和用户字幕修改不丢。旧原件不可用时明确显示来源版本缺失；不能悄悄打开当前新版本的同一页/同一时间点当作旧证据。

“支持恢复与迁移”不自动意味着备份了全部外部原件。业务导出默认不复制几十 GB 文件；若用户以后需要完整原件备份，可以提供独立的显式导出选项，不默认反复复制全视频。

### 4.3 原生文档标识不能代替应用版本

PDF.js 的 `fingerprints` 官方标注不保证唯一；`getPageLabels()` 在未声明时返回 null。Docling 的 JSON pointer 是当前产物中的结构位置，也不能当跨版本永久题号。[PDF.js API](https://mozilla.github.io/pdf.js/api/draft/api.js.html)、[Docling 数据结构](https://docling-project.github.io/docling/concepts/docling_document/)

推荐 locator 绑定 `asset_id + source_revision + artifact_revision + regions + text_quote`；跨页题允许多个 region。只是重新 OCR 也产生新 artifact revision；保留当前索引指针，旧聊天引用原来的区域/快照，不依赖重新编号后的 `#/texts/37`。

## 5. 多持久域的一致性与数据生命周期

### 5.1 不能用一笔 SQL 事务覆盖全部系统

应用 SQLite、应用图片文件、Harness home、远端模型响应是不同持久域，没有天然的跨域原子提交。不能先显示“已保存”、随后才发现题图未写完，也不能借 SQLite rollback 假装撤销已经发生的云端调用。

建议附件发布：临时文件写入 → 完成校验及必要落盘 → 同一数据卷内发布到内容地址 → 短数据库事务建立附件/消息引用 → 执行请求。文件已发布而事务失败时形成暂时孤儿，之后按宽限期回收；数据库已引用的文件缺失则报告真实状态，不能用其他截图顶替。

Python 提供 `fsync`、`replace` 等文件原语，但跨文件系统替换可能失败，原语不等于多对象事务。Windows 上还要验证占用、权限、磁盘满和强制退出场景。[Python 3.12 文件操作](https://docs.python.org/3.12/library/os.html#os.replace)

Harness 实际接收和生成事件通过执行映射补摄入业务层；模型结果已产生但业务事务失败时，恢复要读取原执行，不重新提交用户问题。细节沿用《跨端业务数据与Harness上下文接续设计.md》的 submission、epoch、事件唯一键和 outcome_unknown 规则。

### 5.2 生命周期分层

| 类别 | 保存与清理规则 |
| --- | --- |
| 受保护业务资产 | 聊天、已提交题图、必要编辑原图、用户手改字幕、主动保存内容；不自动当 cache 删除 |
| 来源/产物历史 | 引用中的来源修订、题干快照和必要旧预览；由引用关系决定保留，不能只留最新 |
| 可重建产物 | 当前索引、未引用缩略图、可重做 OCR、纯预览 cache；可按预算回收，但不能冒充已离线可用 |
| 临时任务数据 | 片段音频、未完成下载、临时页面图、未发送且已放弃的编辑临时文件；任务终态与宽限期后清理 |
| 执行记录 | 活动/结果未知 Harness 会话不清理；封存后也先确认业务终态与必要附件已对账，再按明确策略归档 |
| 行为明细 | 近期明细，长期汇总；聚合版本、去重依据与足够恢复信息需保留，避免同步重放重复计时 |

当前原图和提交裁剪图可能是不同字节，Harness 还可能生成规范化附件。**只承诺同一存储域内按内容复用，不宣称全系统天然只存一份。** 单独统计应用资产、Harness 资产和 cache，避免隐藏副本使体积失控。

## 6. 资料解析与找题：分开验证

### 6.1 组件能力不等于学习资料已经可用

| 来源类型 | 现有组件可提供 | 尚需本项目完成 |
| --- | --- | --- |
| 文字 PDF | PDF.js 阅读，pypdfium2 渲染与文本层/字符框 | 阅读顺序、公式、章节题号、跨页题与图形绑定 |
| 中文扫描 PDF/图片 | Docling 等 OCR/版面候选 | 条件/符号正确性、题干完整性、页码与题号、低质扫描效果 |
| DOCX | 原生段落/结构与公式候选 | 原生抽取不等于稳定印刷页；精确页跳转需要版本化 PDF 预览或明确降级段落定位 |
| PPTX | 幻灯片/形状内容、备注等 | 复杂分组旋转、可见层/备注/隐藏内容区分，题图与原幻灯片对应 |
| DOC/PPT 等旧 Office | Harness Office/LibreOffice 转换路径候选 | 真实格式、字体、分页保真与来源版本映射 |

pypdfium2 官方明确不执行词/行/段落版面分析。Docling 承认复杂布局和低质量扫描会产生次优结果；默认 chunking 可能按 token 拆分/合并，因此不能把 chunk 等同于完整题目。[PDFium API](https://pypdfium2.readthedocs.io/en/stable/python_api.html)、[Docling 质量说明](https://docling-project.github.io/docling/concepts/confidence_scores/)、[Docling chunking](https://docling-project.github.io/docling/concepts/chunking/)

今日官方 Word 后端的结构文本没有稳定页 provenance；PPTX 后端具有 slide/形状信息，但有组旋转限制，并读取备注与隐藏层。它们是当前源码观察，锁定发行版需重验。[Word 后端](https://github.com/docling-project/docling/blob/main/docling/backend/msword_backend.py)、[PPTX 后端](https://github.com/docling-project/docling/blob/main/docling/backend/mspowerpoint_backend.py)

### 6.2 公式语义仍是效果风险

Docling 公式增强产物为 LaTeX，额外模型会增加处理耗时，多数增强默认关闭；官方还说明公式裁剪留白可能引入编号或周围文字。**生成可渲染 LaTeX 不证明负号、积分上下限、矩阵行列或分段条件正确。**[Docling enrichment](https://docling-project.github.io/docling/usage/enrichments/)

采用“解析产物＋原页/区域＋题目对象”组合。题目对象至少关联题干、各小问、公式、图形、续页区域和题号类型；“例 3”“习题 3”“第 3 小问”不能合并为同一编号。引用打开位置必须测试旋转页、CropBox、缩放和 DPI，不只测试未旋转文字页。

解析许可仍逐项固定：PDF.js Apache-2.0；pypdfium2 及 PDFium notices；Docling 代码与实际模型许可证分开；Office runtime 及字体/依赖单独记录。不能把整个 OCR/公式链统一写为“MIT”。[Docling 许可](https://github.com/docling-project/docling#license)、[CodeFormulaV2 模型卡](https://huggingface.co/docling-project/CodeFormulaV2)、[pypdfium2 许可](https://github.com/pypdfium2-team/pypdfium2#licensing)

## 7. 增量索引、中文与语义检索

### 7.1 今日重复的局部实测

仅在内存数据库中执行；当前 PATH Python 3.12.5，SQLite 3.45.3：

| 索引输入 | 查询“积分” | 查询“定积分” |
| --- | --- | --- |
| “计算定积分的方法”，默认 unicode61 | 0 | 0 |
| 同一原文，trigram | 0 | 1 |
| “计算 定积分 积分 的 方法”，unicode61 | 1 | 1 |

这证明需要中文预分词与短词策略，**不证明数学资料找题准确率、规模性能或完整知识库已经可用**。FTS5 默认连续 token 规则和 trigram 三字符边界可由官方核对。[FTS5 tokenizer](https://sqlite.org/fts5.html#tokenizers)

关键词路线继续采用 jieba 搜索模式＋数学词典；查询与文档分词版本一致。语义候选继续为 BGE-small-zh-v1.5 CPU＋sqlite-vec：前者是中文通用文本向量，不保证数学公式等价；后者仍标预 v1，需固定版本并保持索引可重建。[jieba](https://github.com/fxsjy/jieba)、[BGE 模型卡](https://huggingface.co/BAAI/bge-small-zh-v1.5)、[sqlite-vec](https://github.com/asg017/sqlite-vec)

### 7.2 增量发布，而非边改原文边混用索引

每次 build 记录：来源/产物修订、分词器和词典版本、embedding 模型 revision/维度、处理范围、索引 generation 与 coverage。

worker 产生候选结果 → 主业务层核对来源/base revision → 在受控批次中写入索引 → 原子切换有效 generation/指针。旧任务晚到则拒绝发布。全文和向量暂未同时完成时，查询明确使用哪个有效分支，不把新 FTS 片段与旧向量文本混装成同一道题。

字幕初稿、纠错稿与手改稿只有有效版本进入检索；保留历史原文，不重复召回。查不到时区分 `not_processed / partial / unavailable / searched_no_match / failed`，不能把未处理片段说成“资料里没有”。

结构化定位优先，模糊题意使用中文关键词与语义候选融合，然后组装完整题目。相似分数不能代替来源版本、题号约束或公式条件校验。用户明确问资料中的题目时，先取原题；截图已足够时整条检索链不运行。

## 8. 容量、缓存与数据库准入

### 8.1 需要测量的规模

几十 GB 是外部原件规模，不是数据库容量。实际增长至少分别记录：应用受保护附件、解析/预览、索引、Harness 执行附件/日志、临时任务文件和备份。

粗算例仅用于预算：512 维 float32 向量每条 2,048 字节；50,000 条约 97.7 MiB，尚未计算索引、元数据与模型运行内存。每天 100 张、平均 1 MiB 的已保存图片，一个月约 2.93 GiB；这是假设，不是用户实测。必须记录实际图片分布、有效文本单元数和产物倍数，不能按视频总字节预测向量规模。

可回收产物设单独预算，任务开始前检查空间，写入失败仍需正确处理；磁盘满时优先暂停后台解析/下载，不能自动删用户聊天或已提交图。旧版本索引只在不被活动查询/快照引用后清理，避免重建时峰值空间翻倍后拖垮前台。

### 8.2 SQLite 准入继续保留

今日官方 WAL 文档仍说明 WAL-reset 修复在 3.51.3+，或官方列出的回移修复版本；本机 3.45.3 不能作为正式 WAL 基线。WAL 要求同主机，长读事务可能妨碍 checkpoint 并使日志持续增长，因此不能在网络流或模型请求期间保持业务读写事务。[SQLite WAL](https://sqlite.org/wal.html)

建立独立环境后查询实际 SQLite 运行库，记录修复证明与 FTS5 能力。主业务层统一短事务写入；Python worker 与 Harness 不共享一份任意可写业务连接。暂时用 DELETE journal 做功能原型时明确这是串行/读写阻塞的回退，不宣称已通过 WAL 验收。

## 9. 备份、导出和 schema 版本

### 9.1 三种不同目的

- **运行备份**：恢复本机业务状态和必需对象；以 SQLite backup API 或受控一致检查点获得数据库，不只复制打开中的 `.db`。[SQLite Backup API](https://www.sqlite.org/backup.html)
- **学习资产导出**：版本化 manifest＋JSONL/标准字幕/图片/来源映射，支持跨软件读取和迁移；不依赖 ORM 私有表长期兼容。
- **Harness 执行归档**：独立原生日志/附件及版本，供原执行恢复与审计；不是安卓业务同步格式。

备份先阻止新执行与清理任务，取得可确认终态/明确未知状态，列出应用对象 manifest 与 Harness 检查点，再保存一致的业务快照。没有跨域原子事务时，备份标注各域的 cut/水位，恢复进行对账；不能把几份目录随手复制后叫作完整一致备份。

### 9.2 导出最小内容

`manifest` 包括 `export_format_version`、应用 schema 版本、实体 ID、内容 hash、附件清单、来源版本及哪些原件未包含。聊天/字幕导出为可读格式，但结构数据保留父关系、修订、实际生成身份和来源；密钥不进入导出。原件默认外部引用，按根目录重新映射。

SQLite schema 版本、导出格式版本、同步协议版本、解析/索引版本和 Harness 执行格式是不同版本轴，不用单个“app_version”隐含全部兼容性。Alembic 能帮助 SQLite 表迁移，但不自动迁移所有文件与跨端消息协议。[Alembic batch migration](https://alembic.sqlalchemy.org/en/latest/batch.html)

导入先校验格式/附件，在 staging 中迁移并建立新对象，最后事务发布；不兼容的较新格式拒绝或只读，不悄悄忽略未知关键字段。相同 bundle 再导入不重复新增聊天和学习时长。已有数据备份后再升级，不要求新版本数据库能被旧程序直接打开。

恢复老业务备份后，Harness 可能仍含更晚结果：按原 submission 对账补摄入，或重建可追溯绑定；**不能自动再次执行备份之后状态不明的问题**。业务资料可用但旧 Harness 会话不兼容时，可用新快照继续同一聊天，不能冒称无损恢复原生推理/工具日志。

## 10. 后续安卓独立使用与同步的实质约束

### 10.1 独立使用不只是电脑网页的另一个窗口

安卓必须本端具有可启动的应用壳、本地业务数据库、资料文件访问、图片输入和模型请求适配。只缓存部分视频而应用启动仍依赖电脑，不能通过“电脑关机独立学习”验收。API 凭据在本端可用但不进入业务同步包；实际 CORS/原生 HTTP、流式图片请求和取消需要设备测试。

PWA 的 IndexedDB/OPFS 等按 origin 管理，默认 best-effort；配额不足会失败，浏览器可能回收存储，`persist()` 也可能返回 false。换端口/域名可能是另一数据域，不能把电脑临时地址变更当成自动迁移。[浏览器存储限制](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)、[StorageManager.persist](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist)

若使用 Capacitor/原生适配，下载的离线课程不能存入可随时被系统回收的 cache；app-specific 持久目录卸载仍会删除，外置卷也可能不可用。用户希望独立于软件存在的导出走共享文件/系统文档选择通道，URI 权限和重启后可用性单独验证。[Android 应用文件](https://developer.android.com/training/data-storage/app-specific)、[Storage Access Framework](https://developer.android.com/training/data-storage/shared/documents-files)

### 10.2 大文件传输不能仅靠“有进度条”

Capacitor 当前 Filesystem 已把下载迁移到 File Transfer，提供原生分块读取；File Transfer 支持上传/下载与 progress，但官方接口不承诺应用进程被杀后的持久断点恢复。其 `chunkedMode` 是流式上传选项，不等于业务的分块重传协议。[Filesystem](https://capacitorjs.com/docs/apis/filesystem)、[File Transfer](https://capacitorjs.com/docs/apis/file-transfer)

建议后续 `TransferManifest` 记录文件 source revision/hash、总大小、已确认字节或块、临时路径和状态；完成校验后再发布 `offline_ready`。恢复下载须检验服务端仍是同一版本，遇到 Range 被忽略、内容变更或磁盘满时不能把新旧字节拼成“成功文件”。HTTP 的 If-Range 有相应条件语义，可作为实现依据，不代替最终内容校验。[HTTP If-Range 规范](https://www.rfc-editor.org/rfc/rfc9110.html#name-if-range)

播放直接使用文件/原生流或本地有界资源路由，不把完整 510 MB 乃至更大视频在 JS 桥中来回 base64。离线保存是完整副本承诺；部分文件只可标“下载中/部分可用”，不能显示为已完成课程。

### 10.3 后台执行与同步边界

Android 对后台数据传输有任务类型与调度限制，不能保证普通 WebView/JS 在锁屏后无限运行。后续最低可靠目标是：前台恢复且连接可用时确定性补同步，后台作为系统允许下的增强；若要求锁屏长下载，再选择适合用户发起传输的原生机制。[Android 数据传输任务选择](https://developer.android.com/develop/background-work/background-tasks/data-transfer-options)

同步先合并业务事实，再处理附件传输和 binding 失效；应用层传输采用 mutation ID、幂等确认、重试、校验与游标。消息先到但图片未到时保留占位，依赖图片的下一次执行等待原附件，不能自动从视频重新补图。

删除需要 tombstone/版本，不能由“某设备此刻没有文件”推断全局删除。回收 tombstone 需要副本确认策略；长时间离线旧设备回归可能要重新取得基线，不能无限依赖已经清理的增量日志。首版保留此契约，安卓阶段再实现协议。

### 10.4 LWW 与播放进度

标题/同一草稿字段/偏好可自动取胜；聊天、附件、实际回答追加合并。因果关系与稳定排序解决收敛，不承诺识别任意断网设备现实中的并发先后。旧修订可保留有限恢复历史，但不弹窗打断正常学习。

播放位置要区分“最后位置”“最远看过位置”“当前播放会话”。用户主动回退到 20 分钟不能被另一端上次的 40 分钟用 max 覆盖；两个端同时播放时也不应互相每秒抢 seek。按明确设备切换/打开时接续，后台心跳不压过新的用户操作，具体规则在安卓阶段验收。

### 10.5 Tailscale 仍只是连接层

Tailscale 提供直连或中继路径，Serve 可以提供私有 HTTPS 服务；均不替应用保存电脑关机期间的聊天、文件和同步队列，也不负责业务冲突。后续分别测试直连/中继、电脑睡眠/关机、地址与权限变化，不能把“ping 通”当视频/同步验收。[连接类型](https://tailscale.com/docs/reference/connection-types)、[Serve](https://tailscale.com/docs/features/tailscale-serve)

## 12. 立项前后应冻结的产物

立项原型应产生：最小业务 schema v1 草案、Asset/Attachment/SourceLocator 约束、submission/执行映射状态图、受保护与可回收数据清单、备份/导出清单、D0 故障样例记录。

Windows 首版详细设计再冻结具体表、目录、缓存预算、任务检查点和可执行恢复流程。资料阶段冻结文档兼容清单、完整题目对象、检索样本与指标；安卓阶段冻结本地存储/大文件下载/同步协议与版本策略。

由此可以先推进 Windows 核心体验，并给后续跨端保留真实可迁移边界；不以“预留接口”冒充完整同步已经完成，也不为未来一次性建设全部基础设施。
