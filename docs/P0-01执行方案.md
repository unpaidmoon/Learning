## 1. 交付目标与边界

本工作包结束时，从项目根目录执行一个开发命令，可启动 React 界面与 FastAPI 后台。界面展示来自真实后台的服务状态；构建后的界面也能由后台同源提供。依赖、类型契约、检查和基础测试均有实际执行记录。

本阶段让后续功能有可靠的开发入口，不把骨架完成称为学习软件可用。Harness 固定制品/学习 preset 属于 P0-02，执行协议属于 P0-03，聊天和附件存储属于 P0-04。此时不接付费 API，不下载模型，不启动 ASR，不实现播放器或移动端，不用模拟回答装饰聊天界面。

实施以本文件的步骤编号推进。遇到环境问题先解决对应步骤，不提前把后续步骤标记通过。

## 4. 实施步骤

### S1：环境预检和版本落定

进入S1前核P0-00/V1的实际结论和恢复实施授权，列仍未覆盖事项。V1通过不等于P0-01已做，V1存在阻断时先处理路线，不靠健康页掩盖。

1. 核对当前文件和用户修改，确认不存在需要保留的应用 manifest；研究 probe 保持原位置和用途。
2. 检查 PowerShell、Node、pnpm、uv 及可用的 Python 3.12 解释器，记录版本与路径。pnpm/uv 不存在时选择项目局部工具安装方式；不擅自更改系统 PATH、全局 Python 或其他项目的环境。
3. 核实前端候选版本的引擎条件，确定本项目工具版本，并写入 manifest、Python 版本文件和环境文档。
4. 在实际选定解释器中查询 `sqlite3.sqlite_version`。未达到现有 SQLite 修复条件时明确记为后续存储限制；不通过替换全局 DLL 解决。P0-01 不启用 WAL，不以此阻断无数据库骨架。
5. 确定本地配置加载次序：命令行显式参数 > 进程环境变量 > 根目录本地 `.env` > 非敏感默认值。配置路径相对项目根目录解析，不随启动时的工作目录漂移。

预检错误应指出缺少的工具、实际发现路径与处理方式。缺少工具时可以完成其他独立文件，不把安装失败解释为代码验收通过。

### S2：建立可重现的项目环境

1. 建立根 pnpm workspace 和最小 `frontend`，设置唯一包名，避免启动器依赖模糊的包匹配。
2. 建立 `backend` 的 src-layout Python 项目，使用项目环境；安装本阶段真正需要的 Web、配置、格式和测试依赖。
3. 首次开发解析生成并提交 `pnpm-lock.yaml` 与 `backend/uv.lock`；后续 bootstrap 使用冻结/锁定安装，不静默更新依赖。
4. `bootstrap.ps1` 检查固定工具版本并安装项目依赖；浏览器测试只准备需要的 Chromium。记录实际发生的下载，不下载 Harness、ASR 模型或整套 Office 运行资源。
5. 根 `.env.example` 仅放 `LEARNING_APP_*` 的非敏感配置示例，如数据根目录、后台端口和前端端口。P0-01 不需要模型密钥；不得加入 `VITE_*` 密钥或真实凭据。

完成判据：重新执行锁定安装不改写锁文件；Python 导入来自项目环境，前端构建使用已固定工具。

### S3：实现最小后台及应用契约

1. 使用应用工厂创建 FastAPI 服务；导入模块不启动服务、子进程或昂贵计算，也不创建学习资料或数据库。
2. 实现 `GET /api/v1/health`。DTO 至少含契约版本、应用版本、后台基础就绪状态和能力状态；后台无法完成自身必要初始化时返回非就绪及非成功 HTTP 状态。
3. Harness、问答、字幕和知识库在此阶段明确为 `not_configured` 或 `not_implemented`。基础就绪只代表业务后台可服务，不代表这些能力已可用；普通响应不返回绝对路径、环境变量或凭据。
4. 建立统一错误结构，至少含稳定 `code` 和可读 `message`；日志不得输出完整配置对象。
5. 从同一应用导出 OpenAPI 到 `contracts/openapi.json`，生成前端类型。增加契约检查命令：临时重建后比对，差异导致检查失败，而非检查时自动修改受跟踪文件。
6. 构建模式由后台提供 `frontend/dist`；API 路由先于 SPA 回退处理，未知 `/api/*` 返回 API 404，不能返回 HTML。构建目录不存在时启动错误明确，不显示空白成功页。

完成判据：健康状态及错误语义有必要测试；不运行 Web 服务也能生成契约；未知 API 与前端页面路由不会混淆。

### S4：实现最小前端及状态交互

1. 建立中文应用入口，展示项目名称、后台连接状态与尚未接入的学习能力。只实现后续可以沿用的布局基础，不设计一整套未来页面。
2. 通过类型化 API 调用真实健康端点，区分连接中、已连接、后台不可达/非就绪，提供一次明确的重新连接操作。
3. 开发模式使用 Vite 的 `/api` 代理；构建模式同源。后台和开发服务默认只监听 `127.0.0.1`，不为联调设置通配 CORS 或自动开放局域网。
   本机地址不等于网页调用授权：后续资产/生成/退出接口要有应用自身会话能力与Host/Origin/WS校验、必要CSRF防护；内部Peer凭据始终只留后台。P0-01不因此引入注册账号体系。
4. 未配置 Harness 时不展示可提交的假聊天入口；不将 fixture 作为实际业务数据，不使用模拟逐字动画冒充模型输出。

完成判据：浏览器显示的后台状态来自真实 HTTP 请求；后台异常时不会继续显示已连接，恢复后可以重新连接。

### S5：实现开发启动和退出

开发默认前端端口 `5173`、后台端口 `8765`，通过项目配置覆盖；测试使用独立端口和临时数据目录。端口只是本项目初始约定，不是硬编码依赖。

启动流程：

```text
pnpm dev
  → 项目 Python 环境启动 learning_app.dev
  → 读取配置，检查端口、依赖和运行目录
  → 启动业务后台与 Vite（隐藏辅助窗口）
  → 等待真实后台健康与前端可访问，成功后显示本地地址
  → 持续观察所属子进程；退出或启动失败时清理
```

- 开发启动器只管理本次启动的前后端；Harness 和 worker 纳管分别随 P0-02/P0-03、B 阶段扩展。
- 端口冲突时报告占用并退出，不杀占用者，不静默连接到其他应用。两个开发实例不能覆盖彼此的运行记录。
- 子进程使用明确参数与专用环境；用 Windows Job Object 或经验证的等效机制管理所属进程树，不能按 `python/node` 名称批量结束进程。实现时验证封装工具产生的孙进程也会被清理。
- 就绪等待有超时；任一服务启动失败时回滚本次启动的其他服务，返回非零退出码。自动重启或重试不形成无限循环。
- 关闭浏览器标签页不结束服务；在开发终端按 Ctrl+C 结束本次实例并释放端口。常驻后台、托盘、任务暂停及正式一键启动体验留在 A-06。
- 本地产物写入忽略的 `.runtime/` 或显式配置的根目录。日志只记录必要诊断，运行记录包含实例身份，不能仅凭一个旧 PID 结束可能已被复用的进程。

构建模式通过 `pnpm start` 启动单个 Python 后台并同源提供静态页面，不保留 Vite 开发服务。它是本地运行入口，不是 Windows 安装包。

### S6：验证、记录并收尾

1. 执行类型、格式、契约和必要测试，修复本次变更引入的问题；不以空测试集合通过作为测试交付。
2. 浏览器访问开发入口，观察真实状态；停止后台确认错误状态，恢复后验证重新连接。
3. 验证 Ctrl+C、端口占用和服务启动失败三类进程行为；确认所属子进程与端口释放，原有进程不受影响。
4. 构建前端，启动单后台入口，验证静态首页、资源、健康 API 与 API 404；确认不依赖 Vite。
5. 再运行一次锁定安装，确认锁文件稳定。记录项目环境实际路径、各工具和 SQLite 版本、命令、退出码和未覆盖项。
6. 更新 README 的真实命令、环境文档和计划状态。只有本工作包的条件全部满足，才将 P0-01 改为“已验证”；其他 P0 和 MVP-A 保持原状态。

## 5. 准备交付的命令接口

**以下均为待实现的命令约定，当前不可直接据此运行。** 初始化后须逐项实际执行，再进入 README 的运行说明。

| 根目录命令 | 预期作用 |
| --- | --- |
| `.\scripts\bootstrap.ps1` | 预检并按固定版本、锁文件准备项目环境与测试浏览器 |
| `pnpm dev` | 一个入口启动开发前后端；显示真实就绪结果，Ctrl+C 清理所属进程 |

| `pnpm contracts:check` | 临时生成并核对契约，无漂移才通过 |
| `pnpm check` | Python Ruff、前端类型/ESLint、约定文件的格式与契约检查 |
| `pnpm test` | pytest 与 Vitest 非 watch 模式，本地确定性测试 |

| `pnpm build` | 生成前端静态资源，构建失败返回非零退出码 |

所有聚合命令保留子命令失败退出码；检查不能通过吞错或跳过不存在的脚本显示成功。首次锁文件生成与后续冻结安装分开记录。

## 7. 风险处理与下一步衔接

| 情况 | 处理方式 |
| --- | --- |
| 候选依赖无法解析或类型/构建不兼容 | 记录冲突链，在既定技术栈内选择兼容版本，更新锁文件；不顺手替换整套架构 |
| 安装源不可达 | 记录具体工具/包与失败步骤；使用可信来源或校验过的现有缓存，不将 probe 目录当依赖路径 |
| 实际 SQLite 未达到 WAL 条件 | 记录限制，P0-04 在项目环境选择修复运行库或明确普通 journal 原型；不改全局 DLL |
| Windows 子进程不能可靠收尾 | 先修复归属与清理，不用进程名全局结束作为通过方式 |
| Harness 尚未接入 | 骨架如实显示不可用；不绕过 Harness 新建正式 DeepSeek 主执行链 |

P0-01完成后，按主计划将V1的固定制品/profile/协议证据经审核产品化到P0-02/03，P0-04接业务持久化、Windows恢复及原P0-05必要历史样例。独立存储工作可按接口并行，不重复建设两套接入/恢复设施。完成骨架不等于P0通过；P0退出需真实图文/活动取消/边界与持久映射实证，不只“有验证路径”。
