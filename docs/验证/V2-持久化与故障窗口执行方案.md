## 1. 目标与前置

证明用户附件、业务消息与Harness执行分属多个持久域时，部分提交/崩溃/重连不会导致已确认资产丢失、错归属或未知请求再次执行。unknown可作为正确业务状态；它与验证“是否按预期保留unknown”的判定分开。

进入条件：

- 已取得对应实施/隔离故障实验授权，明确只动临时fixture目录和本次所属进程。
- P0-04最小业务存储、附件发布、执行映射、事件摄入可运行；无应用时不得以纯mock表结构宣称应用恢复通过。
- V1已有可用执行契约，或本地fixture模拟其固定wire并明确证据级别；故障无需使用真实付费模型。
- 实际SQLite版本、journal、事务/同步设置记录；WAL需已修复运行库，原型DELETE journal明确标注。DB/文件/Harness一致性不由一个SQL事务天然包办。
- runner能在明确故障点停/崩溃本次组件，记录哪个动作已经完成，不能任意sleep猜“可能已经写入”。

## 2. 合成数据与不变量

| fixture | 最小内容 |
| --- | --- |
| COURSE-A/B | 两课程，各有聊天；同一原资料可合法关联两课程，但未关联资料不能借共享文件扩权 |
| SOURCE-v1/v2 | 同一显示文件名的两个内容版本，带稳定资源ID；旧引用必须留v1 |
| ATTACH-A1 | 用户确认选区图与hash；完整原图单独受限，不能自动作为生成附件 |
| CHAT-C1 | U1/A1、当前截图/条件、更正修订；完整历史与模型有效上下文分开 |
| EXTERNAL-U2/A2 | 构造“另一端已完成”的问答，只作为业务记录；不伪造provider事件或usage |
| BINDING | chat→session、epoch、活动submission/generation、事件水位；字段为项目契约，不冒充stock schema |

不变量：已发布消息的必要附件可读取且hash一致；旧输入/截图/来源修订不被新编辑覆盖；一个业务提交只对应一个逻辑生成，实际attempt另记；迟到事件不能改新epoch；任何执行不确定不自动prompt；已完成历史合并不触发旧问题。

## 3. 操作步骤

1. 复制合成fixture至独立临时根目录，记录初始清单/计数/hash；不使用真实业务库。
2. 无故障执行一次“附件落地→消息发布→派发→增量保存→终态入库”，确认故障点事件可观察。
3. 按下表逐例在确定点中断，每例从规定初始快照开始；中断对象只限本次所属组件，保存中断前后记录。
4. 重启同一测试实例，等待恢复/对账；检查业务、附件与Harness三侧身份，而非只看UI最后一条文本。
5. 重复投递同事件/同历史，核唯一键与水位；再运行无故障后续提问，检查没有遗留锁、串聊或自动二次派发。

| 用例ID | 确定故障/操作点 | 预期状态与通过条件 |
| --- | --- | --- |
| V2-01 | 附件安全落地前失败/磁盘写失败 | 消息不显示已保存；草稿/错误可处理，未派发模型 |
| V2-02 | 附件已落地、业务事务未提交时崩溃 | 不发布悬空消息；恢复识别未引用产物，只按明确生命周期处理，不误删用户资产 |
| V2-03 | 消息/输入快照已提交、尚未派发时崩溃 | 可确认未派发的pending可恢复；不得重建第二条业务消息 |
| V2-04 | Harness已接收prompt、业务接收回执丢失 | 查询原执行/映射；不能因无回执再prompt。无法确认保留unknown；fixture派发计数为1 |
| V2-05 | 收到部分流后观察连接断开 | 部分文本保留，恢复snapshot/page并去重；不重新生成同题 |
| V2-06 | Harness终态落盘、业务终态提交前崩溃 | 从原会话对账摄入同一生成；重复恢复不重复消息/usage |
| V2-07 | 业务正文已保存、用量结算缺失/响应断流 | 正文状态与usage已知/未知独立，缺usage不填0，不为补账重答 |
| V2-08 | 同submission连点/重复投递；重复累计事件 | 一个逻辑生成、事件幂等，实际出站数与终态可解释 |
| V2-09 | 旧epoch的增量/终态在新binding后迟到 | 不能覆盖新生成或追加到当前页面；保留诊断归属 |
| V2-10 | C1生成时切COURSE-B，随后回看C1 | B默认按课程新聊，旧生成继续归C1，不串聊；收放/全屏/同课程切资料不新聊 |
| V2-11 | 原件v1被v2覆盖或移动/缺失 | 旧截图/聊天/locator仍绑定v1；缺失明确，不静默跳新版，合法重定位不变资源身份 |
| V2-12 | 外部U2/A2合并两次，再问新U3 | U2/A2各一份、旧问题实际派发数0；必要重建binding，U3实际上下文含允许图/最新修正，UI chat不变 |
| V2-13 | 必需确认附件缺失，或草稿重裁产生新图 | 不静默略过附件/补原帧；旧提交仍指旧裁剪，新草稿独立 |
| V2-14 | 活动cancel与迟到完成/连接断开交错 | 以真实执行/对账定终态，部分内容保留；后续追问不被旧回调改写 |
| V2-15 | 未授权origin/Host/WS、未登记asset/path | 服务端拒绝读资产/发模型/退出；不新增账号系统，Peer凭据不下发浏览器 |

来源/权限负例、反复恢复和无故障后续均需实际观测。纯数据库模拟可验证状态规则，不能证明真实Host断线与恢复。

## 4. 证据与通过标准

每例记录故障点确认事件、源/输入/附件hash、三侧身份和水位、恢复后消息/修订/附件数量、实际模型派发计数、usage存在性、终态/unknown、后续可用性。对账时间单列，不预设服务端“恰好一次计费”。

必须全部满足：已确认发布资产不丢/不串；旧回调隔离；已完成历史不重跑；未知不二次派发；重复事件/计量不重复结算。预期unknown而实际unknown可判该负例通过，但生成是否执行仍未知，不把它写成“恢复了完整答案”。

严重资产/权限/重复请求失败停止相应组，修复发布顺序、唯一键、epoch或对账后复测原窗口及相邻窗口。admission fence若需开发单独记范围，不把它称stock能力或为了追求恰好一次预建全套同步。

## 5. 清理、授权与交付

证据写入本地 run 目录；只清理明确测试临时物，先核绝对路径仍在测试根目录。不得删除真实课程／聊天；执行未知时不通过重跑真实模型补结果，已知失败后的必要修复复测仍按项目级授权自主执行并另留证据。

交付物已包含故障矩阵结果、脱敏事件／资产清单、三侧身份与水位、完整性 hash、派发／usage 与清理记录。正式 Repository、Service、ExecutionAdapter、固定 Host、本地 provider 及真实 HTTP／WS／Chromium 分层验证；最终矩阵 13 次本地 Messages、真实 0，另有高频正式 HTTP 取消相邻回归 1 次本地、真实 0。所有测试只动合成根目录与所属进程，Host／Job 剩余为空，端口关闭。原失败、修复和未覆盖事项在报告保留；预期 unknown 不被写成恢复了完整答案。P0-04 已按本轮范围验收，A-05 完整试用验收仍待 MVP-A。
